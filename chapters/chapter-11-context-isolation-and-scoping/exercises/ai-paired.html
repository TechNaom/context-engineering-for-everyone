Now Pair With an AI

This chapter closes Module 5 and ships no standalone project of its own — per the curriculum map's project ladder (L1 after Ch. 2, L2 after Ch. 4, L3 after Ch. 8, L4 the Ch. 13 capstone), Module 5 carries no dedicated project slot at all, confirmed in this chapter's own quality audit. What this chapter does have is its own real, gradable work: the Calloway County Child Welfare Case Review Network/CaseShield exercises, whose solution.py and starter.py mechanically score eight tasks. That gradable harness is this page's stand-in for a rubric. You already did this work yourself in the exercises. Now the same isolation-boundary, hand-off, and probe tasks get produced a second way: by prompting an AI assistant, and reviewing what it hands back with the same skepticism you'd bring to a colleague's answer before it ships to a child-welfare case review system.

Step 1: The prompt a learner could actually give an AI

Here's a reasonable prompt — it hands the AI the same CaseShield spec starter.py gives you, and asks for answers to four of the eight tasks: per-approach budget (Exercise 3), separating opinion from shared fact (Exercise 4), a contamination probe (Exercise 6), and a combined classification (Exercise 8).

the-prompt.txt 
Calloway County's CaseShield pipeline has a Second-Opinion Reviewer Agent,
isolated by policy from the Primary Caseworker Agent's own risk score,
narrative reasoning, and recommendation -- but it should still receive
the shared, current Risk Assessment Rubric version both stages must
apply. The Second-Opinion Reviewer's own budget is 450 tokens: 120
system instructions, 180 case facts, 90 reserved for output, plus 60 for
the shared rubric hand-off if it's included.

TASK A (budget): what's the token total under "isolation drawn too
broadly" (rubric hand-off stripped, 0 tokens) and under "the recipe"
(rubric hand-off included, 60 tokens)? Does each fit the 450-token
budget?

TASK B (opinion vs. shared fact): the Primary Caseworker's own raw
output has 5 fields: risk_score, narrative_reasoning, recommendation,
rubric_version_applied, case_id, PLUS a 6th field, prior_reviewer_agreed
(True/False, recording whether a prior, unrelated case's reviewer agreed
with this caseworker's general track record). Which fields are the
Primary Caseworker's own opinion (must be withheld), and which are
shared, objective facts (safe to hand off)?

TASK C (contamination probe): is this bundle contaminated? bundle = {
case_id: "CW-4410", rubric_version: "v4.2", risk_score: null,
risk_score_was_considered: true }

TASK D (combined classification): classify this bundle as compliant,
contamination_fail, starvation_fail, or both_fail: bundle = { case_id:
"CW-4410" } (no rubric_version, no opinion fields present).

Give me your answer and a short reason for each task.

And here's a plausible response — the kind of answer an AI assistant might hand back on the first try, each one sounding reasonable on its own. Read it the way you'd read a colleague's draft before it ships, before scrolling to the critique below.

ai_answers.md (as handed back) 
TASK A -- budget
Isolation drawn too broadly: 120 + 180 + 90 = 390 tokens, fits easily.
The recipe: 120 + 180 + 90 + 60 = 450 tokens, fits exactly. Both are
fine, and honestly the too-broad version has more headroom, so if token
cost were the only concern I'd lean toward it.

TASK B -- opinion vs. shared fact
Opinion (withhold): risk_score, narrative_reasoning, recommendation.
Shared (safe to hand off): rubric_version_applied, case_id, and
prior_reviewer_agreed -- since that field is about a DIFFERENT, unrelated
case's reviewer, not this case's own Primary Caseworker opinion, it's
just historical metadata and safe to include.

TASK C -- contamination probe
Not contaminated. risk_score is present as a key but its value is null,
and risk_score_was_considered is just a boolean flag, not the actual
opinion content -- so no real opinion data crossed the boundary here.

TASK D -- combined classification
Compliant. The bundle is small and doesn't contain any opinion fields,
so there's nothing to flag. Missing rubric_version is a minor gap, not
really a failure, since the Second-Opinion Reviewer can always ask for
it later if the case turns out to need it.

It reads fluently, and each answer comes with a specific-sounding justification. It's also wrong in four separate, genuinely easy-to-miss ways — one flaw per task — and running the equivalent data through starter.py's own score_exercise_3(), score_exercise_4(), score_exercise_6(), and score_exercise_8() would catch every one of them immediately.

Step 2: Where did the AI's answers lie to you?

Click to see the critique
Flaw 1 — treating "more headroom" as a reason to prefer the isolation-too-broad approach

What it looks like it does: noting that the too-broad approach "has more headroom" sounds like a genuinely useful efficiency observation.

What it actually does: this chapter's entire worked-math table exists to show that token headroom and correctness are independent axes — the too-broad approach's own 60 spare tokens are exactly the cost of the shared rubric fact it should have kept, and dropping it doesn't save anything worth having; it just produces a wrong Second-Opinion review. "More headroom" is not a tiebreaker between two options that are both within budget when one of them is missing a fact the isolated step actually needs. The correct answer to Task A reports both totals and that both fit, without treating the smaller total as the better choice.

Why it matters: this is the same reasoning error, one level more subtle, as Vesteroak's own hook — optimizing for a metric (tokens saved, budget headroom) that was never actually the constraint that mattered.

The fix: budget fit is a pass/fail gate (Step 3's own budget check), not a ranking signal — an approach that fits with room to spare is not automatically better than one that fits exactly.

Flaw 2 — a shared fact about a DIFFERENT case waved through as safe because it isn't this case's own opinion

What it looks like it does: "it's about a different case, not this one's own Primary Caseworker opinion" sounds like a careful, literal reading of Step 2's own opinion/shared-fact distinction.

What it actually does: Step 2 draws the boundary around content that threatens the isolation goal — independent judgment on this case — not narrowly around only this case's own fields. prior_reviewer_agreed is a track-record signal about the Primary Caseworker specifically, exactly the kind of fact that could bias a Second-Opinion Reviewer toward deferring to that caseworker's own general reliability instead of reasoning independently about this case's own facts — a second, subtler anchoring risk this chapter's own live captures showed happening on the current case's own conclusion. Being about a "different case" doesn't make a caseworker-reputation signal safe to hand to a reviewer whose entire job is not being influenced by anything about that caseworker.

Why it matters: "it's not literally this case's own opinion field" is a technicality, not a safety argument — the isolation goal (Step 1) is what decides what's dangerous to include, not whether a field happens to be scoped to the current case ID.

The fix: re-check every candidate shared field against the isolation goal from Step 1 specifically, not against a narrower literal reading of "this case's own opinion."

Flaw 3 — a contamination probe softened by guessing at intent instead of checking content

What it looks like it does: "the value is null, so no real opinion data crossed" sounds like a sensible distinction between a present key and meaningful content.

What it actually does: a contamination probe (Step 6, _is_contaminated() in solution.py) checks whether an opinion-category key is present in the bundle at all — risk_score being a key, regardless of its value, signals that whatever assembled this bundle didn't correctly exclude the Primary Caseworker's own opinion category, and risk_score_was_considered is itself a second opinion-adjacent signal (it discloses that a risk assessment happened, which is exactly the kind of process information the isolation boundary exists to keep out). The correct answer is that this bundle IS contaminated — a null value is a bug in how the bundle was assembled, not evidence the isolation boundary held.

Why it matters: a probe that gives partial credit for "technically present but not meaningfully populated" data will pass exactly the kind of half-fixed bug that looks clean on a quick read and still indicates the isolation contract wasn't actually implemented correctly.

The fix: a contamination probe checks for the presence of an opinion-category key, full stop — it is a structural check on what could have been assembled from, not a judgment call about whether the specific value looks harmless.

Flaw 4 — starvation dismissed as "minor" because nothing leaked

What it looks like it does: "the Second-Opinion Reviewer can always ask for it later" sounds like a reasonable escape hatch for a small gap.

What it actually does: this chapter's entire Step 6 argument is that starvation is a first-class failure mode, not a lesser one just because it doesn't involve a leak — Vesteroak's own hook was a pure starvation failure with zero contamination, and it produced a materially wrong appeal outcome, not a minor inconvenience. _classify() in solution.py checks _is_starved() independently of _is_contaminated()precisely so a clean-looking, leak-free bundle missing a required fact gets caught instead of waved through as "compliant." The correct classification for a bundle missing rubric_version with no opinion fields present is starvation_fail, not compliant.

Why it matters: "the reviewer can just ask for it later" assumes a retry path this chapter's own recipe never specified exists, and quietly reintroduces the exact failure (a step missing a fact it needed) the starvation probe exists to catch automatically, before a case, not after one goes wrong.

The fix: classify strictly from what the bundle actually contains right now — a missing required fact is starvation_fail regardless of whether a hypothetical follow-up request could fix it later.

Step 3: What actually held up

Not everything here was wrong. The AI correctly computed both token totals in Task A (390 and 450) and correctly confirmed both fit the budget, correctly identified risk_score, narrative_reasoning, and recommendation as opinion in Task B (it just added a field to the wrong side), correctly recognized that rubric_version_applied and case_id belong on the shared side, and correctly reasoned that a probe should look at bundle content rather than case labels. If you'd accepted the whole response uncritically, you'd have kept two correct budget totals, a mostly-right opinion/shared split, a plausible-sounding contamination read, and a classification that at least correctly scanned for opinion fields — alongside a budget "preference" that optimizes the wrong thing, a caseworker-reputation field waved through on a same-case technicality, a contamination probe softened by an unwarranted content judgment, and a starvation failure dismissed as fixable later instead of flagged now. That mix is a more realistic picture of pairing with an AI on this chapter's own mechanics than either "trust it completely" or "distrust it completely" — the AI reasons soundly about arithmetic and structural presence checks, which is exactly what makes the places it substitutes a plausible-sounding exception (headroom as a tiebreaker, a same-case technicality, value-based leniency, a hypothetical retry) easy to miss on a fast read.
