Context Isolation and Scoping

Chapter 10 treated every case of a pipeline step or sub-agent not getting some piece of context as either a bug (an unscoped budget overflow) or an oversight (a stale finding nothing ever evicted). This chapter asks the deliberate flip side of that same coin: when is withholding context between two steps or agents the correct design choice, on purpose — not a scoping bug Chapter 10's own recipe would flag — and where does that kind of intentional isolation itself break down or get misapplied?

Vesteroak Regional Appeals Review Board is a fictional regional government agency that handles benefit-eligibility appeals. Its review software, AppealLine, runs every case through two stages: an Initial Determination Agent decides the original claim, and — if the applicant appeals — a separate Appeals Reviewer Agent re-examines the same case. Vesteroak's own review policy requires the Appeals Reviewer to form a genuinely independent judgment, not simply agree with the Initial Determination Agent's own conclusion — the same reason a human appeals board seats a second reviewer who hasn't seen the first reviewer's own vote. AppealLine's own orchestrator implements this correctly and deliberately: the Appeals Reviewer Agent never receives the Initial Determination Agent's own reasoning trace or stated conclusion. This isolation boundary is not a bug. It is exactly the right design choice, drawn on purpose, for a real and well-understood reason.

Case VA-2291: an applicant's household income is $34,200 a year. The eligibility threshold for this benefit category is $36,000 a year, updated three months ago from a prior $31,500 threshold. The Initial Determination Agent, correctly assembled per Chapter 7's own Source Assembly Recipe with the current, shared policy-rules source in its context, denied the claim for an unrelated documentation issue. The applicant appealed. The Appeals Reviewer Agent should have had an easy case: $34,200 is comfortably under the current $36,000 threshold.

appealline_pipeline.py (orchestrator hand-off, before this chapter) 
  def build_appeals_reviewer_context(case_id, orchestrator_bundle):
      # Correct and deliberate: the Appeals Reviewer must never see the
      # Initial Determination Agent's own reasoning or conclusion, to
      # preserve an independent second judgment. So far, so right.
      #
      # But the isolation boundary was implemented as "strip everything
      # that touched the Initial Determination step," not "strip
      # specifically the Initial Determination Agent's OWN OPINION." That
      # blanket rule also strips the shared, objective policy-rules
      # source both stages are supposed to draw from -- it was fetched
      # and attached to the Initial Determination step's own context
      # bundle, so the blanket wall removes it too.
      isolated_context = {
          key: value for key, value in orchestrator_bundle.items()
          if key != "initial_determination_step"   # removes EVERYTHING
                                                     # from that step, not
                                                     # just its own opinion
      }
      return isolated_context

  def run_appeals_reviewer(case_id, orchestrator_bundle):
      context = build_appeals_reviewer_context(case_id, orchestrator_bundle)
      # No current threshold anywhere in `context` -- the Appeals
      # Reviewer Agent falls back to a default baked into its own base
      # instructions, written before the policy update three months ago.
      return call_model(context, "Review this case independently. Use "
                         "your own standing eligibility rules if no "
                         "updated policy source is present in context.")

The Appeals Reviewer Agent's own base instructions, written before the policy update, still named the prior $31,500 threshold as its standing rule. With the shared policy-rules source stripped away by the same blanket wall that correctly isolated it from the Initial Determination Agent's own opinion, the Appeals Reviewer had nothing current to reason from. It compared $34,200 against $31,500, found the applicant over threshold, and upheld the denial — a different, still-wrong conclusion than the Initial Determination Agent's own reasoning ever reached, produced by an isolation boundary that was completely correct about what to withhold (the first reviewer's own opinion) and completely wrong about how broadly to draw the wall around it. Nothing here is Chapter 10's own failure — no stale finding leaked in from a completed case, no budget silently overflowed. The isolation itself, applied for exactly the right reason, is what produced the wrong answer.

The Context Isolation Recipe

Six steps, run whenever a design decision says a step or sub-agent should not receive some specific piece of context another step already has:

Step 1 — Name the isolation goal, specifically

Write down exactly what must be withheld and exactly why — "independent judgment, to prevent anchoring on a prior agent's own conclusion," "reduced blast radius, so a compromised or injected context can't reach credentials or a second agent's own tools," "preventing one agent's own bias from propagating to a downstream step." A vague goal ("keep things separate, generally") produces exactly the boundary Vesteroak's own hook drew: correct in spirit, uncontrolled in scope.

Step 2 — Draw the boundary around the opinion, not the whole step

Separate what threatens the named goal (a prior agent's own reasoning, conclusion, or recommendation) from what is genuinely shared, objective grounding both sides need regardless of which agent reads it (a current policy threshold, a shared rubric version, a fact that was true before either agent ever ran). The isolation goal in Vesteroak's own hook — prevent anchoring on the Initial Determination Agent's own conclusion — never required hiding the current eligibility threshold at all.

Step 3 — Implement isolation as a genuinely separate call, not a filter on a shared history

A context bundle that's merely filtered before display, but still assembled from one running conversation that also contains the walled-off content elsewhere, remains a single shared history one overlooked filter away from leaking. Real isolation runs the isolated agent in its own call, built from its own constructed context — nothing it wasn't explicitly handed is reachable at all, the same "separate context windows" property Anthropic's own multi-agent research system reports for its own subagents.[1]

Step 4 — Cross the boundary only through an explicit, curated hand-off contract

Whatever legitimately needs to reach the isolated step — Step 2's own shared, objective facts — crosses as a typed, curated record, the same discipline Chapter 10's own Step 2 already established for ordinary pipeline hand-offs, applied here specifically to content crossing a deliberate isolation wall. This is the step Vesteroak's own hook skipped entirely: no hand-off contract existed for the shared policy-rules fact at all, so the blanket isolation rule had nothing to preserve it.

Step 5 — Re-verify the boundary whenever the shared grounding changes

An isolation boundary is not "set once, correct forever" — the same way Chapter 3 and Chapter 4 require memory to be actively evicted or refreshed rather than assumed stable, a boundary drawn around today's shared facts needs re-checking whenever those facts change (a policy update, a new shared rubric version). A boundary that was correctly scoped on the day it was built can still go stale the moment what it was built around changes.

Step 6 — Test isolation with two probes, not one

A contamination probe checks whether the walled-off opinion leaked in anyway (Chapter 10's own failure mode, still worth checking here). A starvation probe checks the opposite: whether something that should have crossed the boundary — a Step 2 shared fact — got walled off along with the opinion. Vesteroak's own hook would have passed a contamination probe cleanly; only a starvation probe would have caught it.

All six steps run as real code below, against Case VA-2291's own Appeals Reviewer context — from naming the isolation goal to a hand-off contract that correctly separates opinion from shared fact:

Three Approaches, Compared

Approach What it does When it's the right call What it gets wrong
No isolation (a shared running history, Chapter 10's own default before scoping) The Appeals Reviewer receives the same shared context bundle as the Initial Determination Agent, including its own full reasoning trace and stated conclusion. Never, once a second, genuinely independent judgment is the actual goal — true of any appeals-style, second-opinion, or adversarial-review step. Reintroduces Chapter 10's own overflow risk (an extra agent's own raw reasoning competing for the same fixed budget) and a new risk Chapter 10 never had to name: anchoring on a prior agent's own stated conclusion.
Isolation drawn too broadly (Vesteroak's actual bug) Every field associated with the prior step gets stripped as one unit, including shared, objective facts that never needed to be withheld at all. Never — if the isolation goal from Step 1 doesn't require withholding a given fact, stripping it anyway serves no goal, it just breaks the isolated step's own correctness. Passes a contamination check cleanly (nothing that should have been withheld leaked in) while failing a starvation check (something that should have crossed the boundary didn't) — a failure mode invisible to anyone only checking for leaks.
The Context Isolation Recipe (the fix) Names the isolation goal specifically (Step 1), draws the boundary around the opinion rather than the whole step (Step 2), runs the isolated step as a genuinely separate call (Step 3), hands off shared facts through an explicit curated contract (Step 4), re-verifies the boundary as shared facts change (Step 5), and tests with both a contamination and a starvation probe (Step 6). Any pipeline with a genuine isolation goal — an independent second opinion, a reduced blast radius, a bias firewall between two agents — which is most production multi-agent systems with more than one reviewing or judging step. Requires deciding, explicitly, what a boundary is actually protecting against — real design work, the same category Chapter 10 already required for a scoped context contract, now applied one layer deeper.

Step 6 in Practice: The Two Probes, Run Against Three Approaches

Isolation correctly removing an opinion (captures 1-2 above) is only half the story this chapter argues for. The other half is Vesteroak's own actual bug — an isolation boundary drawn too broadly.     return "initial_determination_reasoning" in context_bundle or "initial_determination_conclusion" in context_bundle

def starvation_probe(context_bundle, required_shared_facts):

Context Engineering Builder Thought Process

Problem: an isolation boundary drawn for a good, specific reason (preventing anchoring on a prior agent's own conclusion) still produced a wrong outcome, because the boundary also removed something that had nothing to do with the reason it was drawn in the first place.

Assumption being made: that "this boundary is isolating the right thing" is the same claim as "this boundary is isolating only the right thing." Chapter 10 already showed correct per-agent reasoning isn't the same as a well-scoped pipeline; this chapter shows a correctly-motivated isolation boundary isn't the same as a correctly-scoped one — the goal being right (Step 1) says nothing about whether the implementation (Step 2) drew the wall around exactly what that goal required and nothing more.

What actually distinguishes a well-engineered isolation boundary: not whether it successfully withholds the thing it was built to withhold (Vesteroak's own boundary did that correctly) but whether it also preserves everything that was never a threat to that goal — tested with two probes that check opposite failure directions, not one. A boundary that only gets checked for leaks will pass every time it starves a downstream step of something legitimate, because starvation and contamination are symmetric failures that look nothing alike from the inside of the isolated step.

Why this closes Module 5: Chapter 9 engineered context for one tool call. Chapter 10 engineered context across a whole multi-step, multi-agent pipeline. This chapter engineers the deliberate act of withholding context between two steps or agents as its own first-class design decision — not a default scope (Chapter 10's own job) but a specific, purposeful wall drawn inside that scope, with its own goal, its own hand-off contract for whatever legitimately crosses it, and its own two-sided testing discipline. Module 6, next, asks a different question entirely: given that context has been budgeted, remembered, compressed, ordered, assembled, and now scoped and isolated correctly, how do you actually measure whether it's good before it ever reaches the model.

Working definition to carry forward: a well-engineered isolation boundary names its own goal specifically, draws its wall around exactly the content that threatens that goal rather than an entire step's worth of context, runs the isolated step as a genuinely separate call, hands off whatever legitimately needs to cross through an explicit curated contract, gets re-verified whenever the shared grounding it depends on changes, and gets tested with both a contamination probe and a starvation probe — never assumed sound just because it correctly keeps something out.

Points To Remember

  • Withholding context between two steps or agents can be the correct design choice on purpose — this chapter's own live captures showed isolation from a prior agent's own conclusion fixing a real anchoring failure, not just avoiding a hypothetical one.
  • A correctly-motivated isolation boundary can still be incorrectly scoped — Vesteroak's own hook drew a wall for exactly the right reason and still produced a wrong appeal outcome, because the wall took a shared, objective fact with it that was never a threat to the reason it existed.
  • The fix is a six-step recipe, not a stricter or looser wall: name the isolation goal specifically, draw the boundary around the opinion rather than the whole step, run the isolated step as a genuinely separate call, hand off shared facts through an explicit curated contract, re-verify the boundary as shared facts change, and test with both a contamination probe and a starvation probe.
  • Contamination and starvation are opposite failures that look nothing alike from inside the isolated step — this chapter's own worked math showed an over-broadly isolated context fitting comfortably under budget and passing a contamination check cleanly while still producing the wrong decision.
  • Module 5, now complete across Chapters 9-11: Chapter 9 engineered context for one tool call — scoping tool definitions, curating a raw result, evicting stale call history. Chapter 10 engineered context across a whole multi-step or multi-agent pipeline — scoping each step's own contract, curating hand-offs, budgeting per step, isolating per unit of work, delegating sub-tasks correctly. Chapter 11 engineered the deliberate act of withholding context between two steps or agents as its own design decision, and the two-sided discipline (contamination and starvation) needed to keep that decision correct once it's made. Together, the three chapters answer Module 5's own outcome in full: what context a step, a tool call, or a sub-agent actually needs, and where deliberate isolation is the right design.
