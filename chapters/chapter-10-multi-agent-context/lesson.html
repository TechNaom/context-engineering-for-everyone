Context Engineering for Multi-Agent Systems

Chapter 9 asked "what does this specific step actually need" for one tool call. This chapter asks the exact same question at a different scale: across a whole multi-step or multi-agent pipeline, does every step or sub-agent need the full accumulated conversation history and every prior step's raw output, or a scoped subset — and what happens to context that keeps accumulating not across many tool calls, the way Chapter 9's own tool-call history did, but across many pipeline steps and many independent units of work run through the same long-running pipeline?

Points to remember

Heronbrook Regional Grantmaking Alliance is a fictional regional foundation that funds small nonprofits. Its review assistant, GrantPilot, is a four-step pipeline: an orchestrator receives an incoming grant application and delegates it, in sequence, to an Eligibility Agent, a Budget Agent, a Compliance Agent, and finally a Recommendation Agent that synthesizes the first three sub-agents' own findings into a funding recommendation. Every one of Heronbrook's staff reviewers runs GrantPilot in one long-running session across an entire review cycle — dozens of applications processed back to back without restarting the assistant. By the time this chapter's story starts, every sub-agent's own reasoning was correct on its own terms: the Eligibility Agent correctly classified applicants, the Budget Agent correctly compared requested amounts to category caps, the Compliance Agent correctly checked insurance and certifications. Nothing about any individual sub-agent's own judgment failed.

A reviewer asked GrantPilot to generate the funding recommendation for Applicant 12, a youth-education nonprofit requesting $18,000 against a $25,000 category cap — a clean, unremarkable, easily approvable case. GrantPilot's orchestrator had already processed eleven applicants earlier in the same session, several of them correctly flagged and denied for exceeding their own category caps.

grantpilot_pipeline.py (orchestrator hand-off, before this chapter) 
  def run_pipeline_step(step_name, orchestrator_session, step_budget_tokens=400):
      # The orchestrator's own accumulated session history -- every prior
      # applicant processed so far this review cycle, unscoped -- gets
      # appended to EVERY step's own context, on every single call,
      # regardless of which applicant is actually under review right now.
      session_log = "".join(
          format_applicant_record(a) for a in orchestrator_session.all_applicants_so_far
      )
      # No per-step contract decides what THIS step actually needs; no
      # boundary is drawn between "the current applicant's own data" and
      # "everything else this session has ever touched." A crude
      # char-based cutoff is applied wherever the step's own budget runs
      # out, cutting off whatever happens to be appended last.
      return session_log[:step_budget_tokens * 4]

  def run_recommendation_agent(orchestrator_session):
      # By the time Applicant 12 reaches this step, eleven prior
      # applicants' own records are already ahead of it in the log --
      # appended in processing order, current applicant always last.
      context = run_pipeline_step("recommendation_agent", orchestrator_session)
      return call_model(context, "Generate the funding recommendation "
                         "for the applicant most recently added to the log.")

Eleven prior applicants' own records, appended in the order they were processed, ran to roughly 2,500 characters — well past the Recommendation Agent's own 400-token (1,600-character) budget. Applicant 12's own record, appended last because it was the most recently processed, never made it into the truncated log at all. GrantPilot's Recommendation Agent, asked to recommend on "the applicant most recently added to the log," reasoned from whatever record actually survived the cutoff — Applicant 7, a community garden nonprofit that had requested $45,000 against a $40,000 cap and been correctly denied nine applicants earlier — and recommended denying that case, never once reasoning about Applicant 12's own $18,000 request at all. Every sub-agent's own logic was still correct. The Eligibility, Budget, and Compliance agents had each reasoned soundly about the applicants they were actually shown. The failure was entirely in what the orchestrator decided to hand each step: not a scoped, current unit of work, but an ever-growing, unscoped session history with no boundary between one applicant's own review and the next.

What's genuinely new here: Chapter 9 decided what a single tool call earns a place in context — this chapter decides what a given step or sub-agent in a larger pipeline actually needs from everything that came before it, a different question with a different failure mode. DispatchLine's own hook (Chapter 9) lost a field to a character cutoff inside one tool result. GrantPilot's own hook lost an entire applicant's own data to the same category of cutoff, but applied to an ever-growing, multi-unit-of-work session history spanning many pipeline steps and many independent applicants, not one result from one call.

The Pipeline/Multi-Agent Context Recipe

Six steps, run on a pipeline's own per-step hand-offs before any individual step's own context is assembled:

Step 1 — Define each step's own scoped context contract

Decide, per step or sub-agent, exactly which upstream facts and which prior steps' outputs it actually needs — never "everything the session has accumulated so far." GrantPilot's own Recommendation Agent needs the current applicant's own three sub-agent outputs; it does not need any other applicant's own record, and it does not need the Eligibility Agent's own full reasoning transcript, only its resolved finding.

Step 2 — Pass prior steps' outputs as curated, typed results, never raw transcripts

A prior step's own output is, functionally, the same category of thing Chapter 9 already taught how to handle: a result that needs curating before it enters the next step's context, not a raw dump of everything that step reasoned through to get there. Anthropic's own reporting on building a multi-agent research system states this directly: "each subagent might explore extensively... but returns only a condensed, distilled summary of its work"[1] — the next consumer, whether a step or the orchestrator itself, receives the resolved finding, not the exploration that produced it.

Step 3 — Budget each step's context as its own explicit ledger line item

A four-step pipeline is not one shared context budget split implicitly across four steps — each step gets its own line in Chapter 2's own ledger, sized to what that step's own scoped contract (Step 1) actually requires. Sharing one global budget across every step is exactly what let GrantPilot's own unscoped, ever-growing session history crowd out Applicant 12's own data by the time it reached the Recommendation Agent.

Step 4 — Isolate context per unit of work

Between one applicant's own review and the next, reset or evict whatever working context was scoped to the prior unit of work — a new applicant's review should never inherit the previous applicant's own findings sitting unmarked in a shared working context. This is the pipeline-scale version of Chapter 9's own Step 5 tool-call-history eviction, but keyed on a different boundary: not "the same tool re-called," but "a new, independent unit of work has begun."

Step 5 — Give a sub-agent only its own delegated sub-task, not the orchestrator's full history

A sub-agent needs an objective, an output format or contract, and the specific data its own task requires — not the orchestrator's entire conversation history with every other sub-agent this session. Anthropic's own multi-agent engineering guidance states this as a design requirement directly: "each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"[2] — task boundaries a sub-agent handed the orchestrator's full history has no way to infer on its own.

Step 6 — Hand the pipeline's resolved final output downstream as one well-formed record

The last step's own resolved output — GrantPilot's own funding recommendation — is handed to whatever consumes it next (a reviewer's own dashboard, or Chapter 7's own Source Assembly Recipe if it becomes one source among several) as a single, typed, curated record. Nothing about the pipeline's own internal, per-step working context should leak out to a consumer that was never part of the pipeline in the first place.

All six steps are small enough to run as real code, not just describe -- here they are as an executed, runnable pipeline against Heronbrook's own Applicant 12 review, from scoping the Recommendation Agent's own context contract down to a resolved, isolated hand-off:

full_pipeline.py (executed this session, real output) 
STEP_CONTEXT_BUDGET_TOKENS = {
    "eligibility_agent": 300, "budget_agent": 350,
    "compliance_agent": 300, "recommendation_agent": 400,
}
PRIOR_APPLICANTS_PROCESSED = 11
RAW_OUTPUT_TOKENS_PER_PRIOR_APPLICANT = 180

APPLICANT_12_CURATED_OUTPUTS = {
    "eligibility_agent": {"status": "eligible", "category": "youth_education", "tokens": 30},
    "budget_agent": {"requested_amount": 18000, "cap_for_category": 25000, "over_cap": False, "tokens": 55},
    "compliance_agent": {"insurance_current": True, "certifications_current": True, "tokens": 40},
}

def step2_curate_prior_step_outputs(prior_outputs):
    return {k: {kk: vv for kk, vv in v.items() if kk != "tokens"} for k, v in prior_outputs.items()}

def step3_budget_step_context(step_name, curated_payload_tokens, ledger):
    budget = ledger[step_name]
    return curated_payload_tokens, budget, curated_payload_tokens <= budget

def step4_isolate_unit_of_work(current_applicant_id, session_history):
    return {aid: data for aid, data in session_history.items() if aid == current_applicant_id}

# Naive: full 11-applicant session history handed to the Recommendation Agent.
naive_tokens = PRIOR_APPLICANTS_PROCESSED * RAW_OUTPUT_TOKENS_PER_PRIOR_APPLICANT + sum(
    v["tokens"] for v in APPLICANT_12_CURATED_OUTPUTS.values())
# Scoped: only Applicant 12's own three curated sub-agent outputs.
scoped_tokens = sum(v["tokens"] for v in APPLICANT_12_CURATED_OUTPUTS.values())
fit_tokens, fit_budget, fits = step3_budget_step_context("recommendation_agent", scoped_tokens, STEP_CONTEXT_BUDGET_TOKENS)

Three Approaches, Compared

Approach What it does When it's the right call What it gets wrong
Unscoped, ever-growing session history (GrantPilot's actual pipeline) Every step, on every call, receives the orchestrator's full accumulated session history across every applicant processed so far, truncated by raw character count wherever the step's own budget runs out. Never, once a pipeline runs more than one unit of work per session or has more than one step — true of nearly every real multi-step or multi-agent system. GrantPilot's exact failure: the current applicant's own data, appended last, gets truncated away entirely once eleven prior applicants' own records fill the budget first.
Per-step scoping, but no unit-of-work isolation Each step correctly receives only the current applicant's own data and the specific prior-step outputs its own contract calls for, but the orchestrator never resets working context between one applicant's review and the next. A real, worthwhile improvement over unscoped history — worth doing regardless — but not sufficient alone. Correctly scopes what each step needs from the pipeline's own current pass, but a prior applicant's own finding can still linger in a shared working context and bleed into the next applicant's own review.
The Pipeline/Multi-Agent Context Recipe (the fix) Defines each step's own scoped context contract (Step 1), passes prior steps' outputs as curated results (Step 2), budgets each step's context as its own ledger line (Step 3), isolates context per unit of work (Step 4), gives each sub-agent only its own delegated sub-task (Step 5), and hands the pipeline's final output downstream as one well-formed record (Step 6). Any pipeline that processes more than one independent unit of work per session, delegates to more than one sub-agent, or runs more than one step — true of nearly every real production multi-step or multi-agent system. Requires deciding a per-step context contract and a unit-of-work boundary in advance — real design work, the same category Chapter 9 already required for tool scoping and result curation, not a new class of cost.

No arithmetic bug turned up here -- like Chapter 9's own re-verification, this chapter's worked-math table checked out exactly as written, reported honestly rather than assumed. The fix was never "give every step a bigger budget" (the naive approach overflows every single step's own budget by more than 5x — no individually reasonable per-step budget survives an unscoped, ever-growing session history for long) or "shrink what each sub-agent reports" (each sub-agent's own curated output is already lean; the naive pipeline's own cost comes entirely from carrying eleven other applicants' own records into every step, not from any one sub-agent's own output being too verbose). The fix was deciding, on purpose, which applicant's own data and which prior steps' curated outputs each step actually needed — and drawing a hard boundary at each new applicant's own review.

Step 4 in Practice: Unit-of-Work Isolation and the Ledger Interplay

One more failure mode this chapter's own recipe exists to prevent, shown as real code rather than just described: what happens between two consecutive units of work when a step's own working context is never reset, and how a single pipeline step's own token budget breaks down as its own line items inside Chapter 2's own ledger -- a new line item this chapter adds that Chapter 9 never had to budget for on its own: prior-step curated outputs.

ledger_and_eviction.py (executed this session, real output) 
APPLICANT_12_ELIGIBILITY_FINDING = {"applicant": "applicant_12", "status": "eligible", "category": "youth_education"}
APPLICANT_13_INTAKE = {"applicant": "applicant_13", "org_type": "nonprofit", "category": "senior_services",
                        "requested_amount": 22000}
NAIVE_WORKING_CONTEXT_CARRIED_FORWARD = [APPLICANT_12_ELIGIBILITY_FINDING, APPLICANT_13_INTAKE]

def step4_evict_between_units_of_work(working_context, new_unit_id):
    return [item for item in working_context if item.get("applicant") == new_unit_id]

evicted_context = step4_evict_between_units_of_work(NAIVE_WORKING_CONTEXT_CARRIED_FORWARD, "applicant_13")

Context Engineering Builder Thought Process

Problem: every sub-agent in a pipeline reasons correctly about whatever it's actually shown, and the pipeline's own final output is still wrong, either because the current unit of work's own data got crowded out by an ever-growing session history (GrantPilot's own hook, and this chapter's first live capture) or because a resolved finding from a completed unit of work bled into a new one that hadn't reached that same conclusion yet (this chapter's second live-capture pair).

Assumption being made: that "every sub-agent reasons correctly" is the same claim as "the pipeline produces the right answer." Chapter 9 already showed correct tool execution isn't the same as a well-formed tool-result source; this chapter shows correct per-agent reasoning isn't the same as a well-scoped pipeline, and adds a failure mode Chapter 9's own single-tool-call scope never had to name — contamination across independent units of work processed by the same long-running pipeline, not staleness within one unit's own tool-call history.

What actually distinguishes a well-engineered pipeline hand-off: not whether each step's own reasoning is correct in isolation (every approach in this chapter's own comparison table achieves that) but whether each step's context contract was scoped on purpose, whether that scope was budgeted as its own ledger line, whether prior steps' outputs arrived curated rather than as raw transcripts, whether context was isolated at each unit-of-work boundary, and whether a sub-agent received only its own delegated sub-task rather than the orchestrator's entire session.

Why this continues Module 5: Chapter 9 engineered context for one tool call. This chapter engineers context across a whole multi-step, multi-agent pipeline processing many independent units of work in one long-running session. Chapter 11, immediately next, asks a related but distinct question this chapter deliberately left open: when is withholding context between steps the right design choice on purpose, rather than an accidental omission this chapter's own recipe would otherwise call a bug?

Working definition to carry forward: a well-engineered multi-agent or multi-step pipeline gives each step its own scoped context contract, passes prior steps' outputs as curated, typed results rather than raw transcripts, budgets each step's context as its own explicit ledger line, isolates context at every unit-of-work boundary so one case's own resolved findings never bleed into the next, and gives every sub-agent only its own delegated sub-task — never assumed well-scoped just because every individual step's own reasoning happens to be correct.

Points To Remember

  • Every sub-agent in a pipeline reasoning correctly about what it's shown is not the same as the pipeline producing the right answer — this chapter's live captures showed a truncated, unscoped session history producing a confidently correct answer about the wrong applicant entirely.
  • An unscoped, ever-growing session history is a token cost that compounds with every additional unit of work processed in the same long-running session — GrantPilot's own naive pipeline overflowed every single step's own budget by more than 5x after just eleven prior applicants.
  • The fix is a deterministic six-step recipe, not a bigger budget: scope each step's own context contract, pass prior steps' outputs as curated results, budget each step as its own ledger line, isolate context per unit of work, give sub-agents only their own delegated sub-task, and hand the final output downstream as one well-formed record.
  • Per-step scoping without unit-of-work isolation is a real, worthwhile improvement over unscoped history — but it does not, on its own, stop a resolved finding from one completed unit of work bleeding into the next one's own working context.
  • A sub-agent's own correct reasoning about the wrong scope looks, on the surface, exactly like a correct answer — the model's logic in this chapter's first live capture was entirely sound about Applicant 7; the only thing wrong was that Applicant 7 was never the applicant under review.
