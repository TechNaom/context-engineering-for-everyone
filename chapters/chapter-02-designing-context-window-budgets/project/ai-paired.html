Chapter 2 — Solo → AI-Paired → Critique 20 min

Now Pair With an AI

You already did this yourself in the project — allocated ALLOCATION across L2, L3, and L4 for Halveston's Post-Discharge Follow-Up request type, defended it in PROFILE_JUSTIFICATION, validated it against the given worst-case numbers, and planned a follow-up for anything in deficit. That work stands unchanged; this page is additive. Now the same allocation gets produced a second way: by prompting an AI assistant, and reviewing what it hands back with the same skepticism you'd bring to a coworker's budget spreadsheet before it goes to Halveston's engineering lead.

Step 1: The prompt a learner could actually give an AI

Here's a reasonable prompt — it hands the AI the same spec starter.py gives you, and asks for the same four things the project asks for: an allocation, a profile justification, a validation, and a follow-up plan.

the-prompt.txt 
Halveston Regional Health System's patient-messaging assistant, IntakeLine,
is shipping a new request type: "Post-Discharge Follow-Up" -- a recurring,
multi-session conversation reviewing a discharged patient's medications,
comorbidities, and recovery progress over several weeks, spanning 12-25
turns per session, with a moderate amount of retrieved grounding content
(discharge instructions, medication-interaction lookups) and a genuinely
heavy recalled-memory need (full medication list, comorbidities, and notes
from prior follow-up sessions).

The spec:
  Context window:            48,000 tokens
  Reserved output (Line 5):   2,500 tokens (fixed)
  System instructions (Line 1): 1,200 tokens (fixed)

A worst-case content audit of real Post-Discharge Follow-Up sessions found:
  Grounding Context (L2) worst case:        9,000 tokens
  Conversation History (L3) worst case:    16,000 tokens
  Recalled Long-Term Memory (L4) worst case: 12,000 tokens

Using a five-step Budget Allocation Recipe (fix the hard limit; reserve
Working Space first; fix System Instructions; split what's left across
Grounding Context, Conversation History, and Recalled Long-Term Memory by
this request type's real profile; validate against the worst realistic
case), give me: (1) a token allocation across L2, L3, and L4, (2) a
justification for that split tied to this request type's actual shape,
(3) a surplus/deficit validation for each line against the worst-case
numbers above, and (4) a follow-up plan naming a real technique for
anything in deficit.

And here's a plausible response — the kind of allocation an AI assistant might hand back on the first try. Read it the way you'd read a colleague's budget spreadsheet before it goes to Halveston's engineering lead, before scrolling to the critique below.

ai_allocation.py (as handed back) 
# Post-Discharge Follow-Up is a recurring, moderately long conversation
# with a heavy memory need, so History gets the largest single share and
# Memory gets real weight too, ahead of Grounding.
ALLOCATION = {
    "L2": round(48_000 * 0.30),  # 14,400
    "L3": round(48_000 * 0.45),  # 21,600
    "L4": round(48_000 * 0.25),  # 12,000
}
# 14,400 + 21,600 + 12,000 = 48,000

PROFILE_JUSTIFICATION = (
    "We chose 30% grounding, 45% history, and 25% memory because that "
    "split balances all three lines reasonably for a recurring "
    "conversation type. This gives history the most room since it's the "
    "largest share, with grounding and memory splitting the rest."
)

# Compare each line's allocation against the worst-case numbers.
VALIDATION = {
    "L2": "surplus",  # 14,400 > 9,000
    "L3": "surplus",  # 21,600 > 16,000
    "L4": "surplus",  # 12,000 covers the 12,000 worst case exactly
}

FOLLOW_UP_PLAN = (
    "All three lines have adequate headroom against the worst-case audit, "
    "so no further action is needed before this request type ships."
)

It looks like a real allocation — three lines filled in, a sum that lands on a round number, a justification paragraph, a validation table, a follow-up plan. It's also wrong or weak in three separate, genuinely easy-to-miss ways, and if you dropped these values into starter.py unchanged, its self-check would catch at least one of them immediately — but not all three, because the self-check only verifies internal consistency against your own numbers, not whether your reasoning is any good (exactly the distinction Criterion 5 of RUBRIC.md asks you to be able to explain).

Step 2: Where did the AI's allocation lie to you?

Click to see the critique
Flaw 1 — the percentages were applied to the full context window, not the remaining budget

What it looks like it does: round(48_000 * 0.30) reads like a completely ordinary percentage-split calculation, and the three numbers do add up cleanly to a round 48,000 — nothing about the arithmetic looks broken at a glance.

What it actually does: 48,000 is CONTEXT_WINDOW_TOKENS, the raw window size — not the number these percentages were supposed to split. Per this chapter's own recipe, Steps 2 and 3 reserve Line 5 (2,500 tokens) and Line 1 (1,200 tokens) first, leaving a real remaining budget of 48,000 − 2,500 − 1,200 = 44,300 tokens for L2, L3, and L4 to split. The AI's allocation sums to 48,000, which is exactly 3,700 tokens over the real remaining budget — and 3,700 is not a random overshoot, it's precisely RESERVED_OUTPUT_TOKENS + SYSTEM_INSTRUCTIONS_TOKENS, the two lines the AI's split silently never subtracted.

Why it matters: this is the exact shape of mistake Chapter 1's own hook (SignalDesk) made and this chapter's Step 2 exists specifically to prevent — computing "how much room is left" without reserving output and system instructions first, so the number you split looks bigger than it really is. Ship this allocation unchanged and the request-assembly code either silently overruns the real window by 3,700 tokens, or some later, unplanned truncation has to claw those tokens back from somewhere with no policy behind which line loses them.

The fix: compute remaining = CONTEXT_WINDOW_TOKENS - RESERVED_OUTPUT_TOKENS - SYSTEM_INSTRUCTIONS_TOKENS first (44,300), then split percentages against that number — exactly what starter.py's own remaining_budget() helper does, and exactly why its self-check would reject this allocation the instant you ran it: "ALLOCATION values must sum to exactly 44,300 ... got 48,000."

Flaw 2 — the justification restates the percentages instead of defending them

What it looks like it does: it's a real paragraph, in real sentences, that mentions the request type ("a recurring conversation type") and explains the split — it reads like a justification.

What it actually does: re-read it closely: "history gets the most room since it's the largest share" is circular — it justifies giving history the largest share by pointing out that history has the largest share. Nothing in the paragraph engages with Post-Discharge Follow-Up's actual, specific content shape given in the spec: a full medication list, comorbidities, and notes from prior follow-up sessions — a recalled-memory need this chapter's own hook (Vantry's Chronic Care Check-In) already showed can be the dominant, safety-critical line in exactly this kind of recurring healthcare conversation. The AI's split even under-weights L4 (25%) relative to L3 (45%) without ever addressing why memory, not history, isn't the dominant line here.

Why it matters: this is precisely the failure mode RUBRIC.md's Criterion 2 scores a 2 for: "a justification is present but generic ... without tying the reasoning to this request type's specific content shape." It would pass a naive "is there text in this field" check while still failing the actual bar the project cares about — the same "structural, not correctness" gap Criterion 5 asks you to name out loud.

The fix: tie the split to the request type's real content, the way solution.py does — naming the specific reason memory (or history, if you genuinely believe history dominates) deserves its share: "the recalled record (full medication list, comorbidities, notes from prior sessions) is what keeps a multi-week follow-up safe, so Line 4 gets real weight above the lesson's own long_recurring archetype's 25%" is a defensible, specific claim; "history gets the most room since it's the largest share" is not a claim at all.

Flaw 3 — Line 4's validation call is wrong at exactly the boundary case, and it hides a real deficit

What it looks like it does: "12,000 covers the 12,000 worst case exactly" sounds like a clean, comfortable match — the allocation hits the worst-case number right on the nose, no waste, no shortfall.

What it actually does: "covers exactly" is not the same as "surplus." The project's own rule (spelled out in starter.py's check_validation()) is "surplus" if allocated > actual else "deficit" — strictly greater than, not greater-or-equal. An allocation that lands exactly on the worst-case number leaves zero headroom for anything the audit didn't happen to measure (a slightly longer medication list next month, one more comorbidity note) — that's a deficit by definition, not a surplus, and the AI's plain-language reasoning ("covers it exactly") papered over the strict inequality the actual rule depends on.

Why it matters: this is exactly what RUBRIC.md's Criterion 3 means by "one of three lines is misclassified" (a 2, not a 4) — and it's not a cosmetic slip, because the AI's FOLLOW_UP_PLAN then compounds it: believing all three lines are in surplus, it concludes "no further action is needed," when a correct validation would have flagged L4 as a real deficit needing a real plan — exactly the kind of silent, boundary-case gap that broke Talia's medication check in this chapter's own hook, where a line sized to the exact wrong number, not a generously wrong one, is what let a critical fact get truncated.

The fix: classify L4 as "deficit" (allocated equals, but does not exceed, the worst case), and give it a real follow-up plan instead of "no further action" — name a concrete technique (e.g. summarizing older follow-up sessions' notes into a compact running record, freeing real headroom above the exact worst-case number) and point to Chapter 3, the chapter that owns short-term and long-term memory compression, exactly as solution.py's own FOLLOW_UP_PLAN does for its (different, but analogously boundary-tight) Line 3 deficit.

Step 3: What actually held up

Not everything here was wrong — worth noticing that too, since a fair critique isn't just a hunt for flaws. The AI's arithmetic (once you correct which total it should have split) was mechanically clean — three positive integers, correctly rounded, summing to a consistent total — and giving History real weight in a 12-25-turn recurring conversation type is a genuinely defensible call, not a wrong one (it's simply a different, legitimately arguable split from solution.py's memory-dominant one, since the profile choice is intentionally open-ended per RUBRIC.md). L2 and L3's surplus calls were also both correct. If you'd accepted the whole response uncritically, you'd have kept a mechanically sound split concept and two correct validation calls alongside a wrong subtraction base, a hollow justification, and one dangerously wrong boundary classification that erased a real deficit. That mix — mostly plausible, wrong in specific load-bearing spots — is a more realistic picture of what pairing with an AI actually produces than either "it's always right" or "it's always wrong."
