Designing Context Window Budgets

Chapter 1 named the five-line Context Budget Ledger and used it to diagnose a failure after it already happened. This chapter teaches the other half of the skill, the half a working context engineer uses far more often: allocating a real token budget across all five ledger lines for a specific request type and a specific model's hard context-window limit, on purpose, before a single request is ever sent.

Vantry Health Network is a fictional regional healthcare provider. Its patient-facing chat assistant, TriageLine, launched with real context-engineering discipline behind it — the team had read exactly the kind of lesson Chapter 1 teaches, and refused to ship an unbounded, unmanaged request the way Brackwater's SignalDesk once did. For TriageLine's first request type, "New Symptom Triage" (a patient describing a new symptom, three to six turns, an escalation recommendation at the end), the team measured real conversation lengths, sized the model's 32,000-token context window, and wrote down an explicit budget across all five ledger lines before writing a line of request-building code. It worked. Every audit was clean, every load test passed.

Eight months later, the product team ships a second request type on the same assistant: "Chronic Care Check-In," a longer, recurring conversation for patients managing an ongoing condition — reviewing recent lab results, current medications, and any dosage changes since the last check-in. The engineer assigned to ship it, under a normal deadline, does something that feels completely reasonable: TriageLine already has a working, audited budget. She reuses it exactly, line for line, rather than re-deriving one for the new request type.

triageline_budget.py (the budget config, reused unchanged for a new request type) 
  # Derived and load-tested for "New Symptom Triage" -- short
  # conversations, light medication history, no lab data.
  BUDGET = {
      "context_window_tokens": 32_000,
      "L5_working_space": 3_000,     # reserved output
      "L1_system_instructions": 1_000,
      # Remaining 28,000 tokens split by New Symptom Triage's profile:
      "L2_grounding_context_pct": 0.45,   # symptom knowledge base
      "L3_conversation_history_pct": 0.35, # short, 3-6 turn conversations
      "L4_recalled_memory_pct": 0.20,      # allergy list only
  }

  # request_type="chronic_care_checkin" now reuses BUDGET unchanged --
  # no new profile was derived for a conversation type with a
  # completely different shape: 12-20 turns, full medication list,
  # recent lab panels, comorbidity history.
  def build_request(request_type, patient_context):
      return assemble_context(BUDGET, patient_context)

For the first few weeks, Chronic Care Check-In looks fine in spot checks — reviewers happen to test with patients on short medication lists. Then a patient named Talia, managing a long-standing anticoagulation therapy, has a check-in where her cardiologist recently changed her dosage of warfarin. TriageLine's recalled-memory line (Line 4), sized at 20% of the budget because that was right for New Symptom Triage's short allergy list, cannot hold Talia's full medication list plus the fresh lab panel. The context-assembly code, under pressure to fit the line's fixed token cap, truncates the medication list alphabetically once it exceeds budget — and "warfarin," alphabetically late, is exactly the entry that gets cut. TriageLine reviews Talia's other medications for interactions, finds none, and gives an all-clear that never actually checked the one medication whose dosage had just changed.

Nothing about this incident is a repeat of Brackwater's failure. TriageLine has a real budget, a real reserved output allowance, a real system-instructions line — every lesson from Chapter 1 was followed. The gap is narrower and easier to miss: a budget derived correctly for one request type was applied unchanged to a second request type with a fundamentally different shape, and nobody re-derived the allocation before shipping it. That is this chapter's actual subject.

Why Allocation, Not Just Diagnosis

This chapter uses Chapter 1's five-line ledger as a lens, not a fresh mental model — if the names System Instructions, Grounding Context, Conversation History, Recalled Long-Term Memory, and Working Space aren't already familiar, Chapter 1 is the place to get that vocabulary, not here. What Chapter 1's own project asked you to do was diagnose an existing system's gaps, after the fact, the way a real review finds them. This chapter asks a different, earlier question: given a request type you haven't shipped yet, and a specific model's hard context-window limit, what should each of the five lines get, on purpose, before the first real request goes out the door?

That distinction matters because it's the one Talia's incident shows directly: TriageLine's team didn't skip budgeting the way Brackwater's team did. They budgeted once, correctly, for one request type — then treated that budget as a property of the system rather than a property of the request type it was derived for. A context-engineered feature needs a real allocation for every distinct shape of request it serves, not one allocation copied everywhere convenient. This chapter's own positioning against the course's neighbors is exactly what Chapter 1's "Why This Course Exists" section already stated in full — this chapter doesn't re-argue it, only applies it one level deeper: a well-managed prompt template (`ai-engineering-for-everyone` Chapter 3) and a good retriever (`rag-for-everyone`) still won't tell you how many of the retriever's tokens actually fit next to this request type's conversation history and recalled memory inside a fixed window — that arithmetic is this chapter's job.

The Budget Allocation Recipe

A production model provider's own guidance is direct about the order this has to happen in: "to stay within context window limits, use the token counting API to estimate token usage before sending messages" — allocation is a before-the-request discipline, not an after-the-fact cleanup.[1] Five steps, run in order, every time a new request type ships:

Step 1 — Fix the hard limit

Start from the actual model's real context-window size, not a round number you assume. Context-window size is a property of the specific model you call — provider documentation confirms this varies model to model, sometimes by an order of magnitude within the same provider's own lineup.[2] Whatever number you use here is Step 1's only job: get the actual ceiling right before doing any arithmetic against it.

Step 2 — Reserve Working Space (Line 5) first, not last

Every token the model generates also counts against the same fixed window a request's input competes for — providers are explicit that the context window "holds the conversation history plus the new output" the model generates, not input alone.[1] Reserving Line 5 first, sized to this specific request type's expected response length, is what makes every later line's real available budget honest instead of optimistic.

Step 3 — Fix Line 1 (System Instructions)

Small and stable by design (per `ai-engineering-for-everyone` Chapter 3's own discipline) — measure its real token count once per request type (system instructions can legitimately differ by request type, e.g. a stricter safety preamble for a clinical request type) and treat it as a fixed subtraction, not something to re-negotiate per request.

Step 4 — Split what's left across Lines 2, 3, and 4 by this request type's real profile

This is the step Talia's incident skipped. The remaining budget (window minus Line 5 minus Line 1) does not split evenly, and it does not split the same way for every request type — a short, single-turn lookup and a long, memory-heavy recurring conversation have genuinely different shapes, and Section 4 below gives concrete starting profiles for common request-type archetypes.

Step 5 — Validate against the worst realistic case, not the median

Talia's medication list wasn't the typical case reviewers happened to test — it was a real but less common shape the allocation had to survive anyway. Validate every new allocation against the longest conversation, the fullest recalled-memory record, and the largest grounding-context pull this request type plausibly produces, not the case that's easiest to demo.

Request-Type Profiles: Why One Split Doesn't Fit All

Step 4 needs a real starting point, not a guess made fresh every time. These four archetypes cover most production request types; treat the percentages as a starting allocation to validate against real data for your own system, not a fixed law.

Request-type archetype L2 Grounding L3 History L4 Recalled Memory Why this shape
Short, single-turn lookup (e.g. New Symptom Triage) 45% 35% 20% Little history to carry, grounding does most of the real work.
Long, recurring conversation (e.g. Chronic Care Check-In) 35% 40% 25% History grows fastest across many turns; memory needs real headroom for a full record, not a short list.
Tool-heavy agentic turn 55% 25% 20% Grounding here includes tool definitions and tool results, which routinely dominate — this is a starting placeholder Chapter 9 builds into a real profile in depth.
Long-document review 65% 20% 15% One dominant grounding source (the document) crowds out most other lines by design, not by accident.

Notice Line 1 and Line 5 aren't columns here — they're fixed subtractions from Step 2 and Step 3, decided once per request type before this table's percentages ever apply to what's left.

Worked Math: TriageLine vs. Chronic Care Check-In

Run the actual numbers from the hook, the way a real allocation review would, both for the allocation that shipped and the one that should have shipped.

Two things happen at once when a budget is reused across request types without re-deriving it, and both are visible in the middle column above: Line 2 sits 2,900 tokens over-provisioned — real budget wasted on a line that didn't need it — while Lines 3 and 4 sit 3,200 and 1,400 tokens under-provisioned, forcing an emergency truncation with no real policy behind which content gets cut. That's exactly the alphabetical medication-list truncation that dropped Talia's warfarin entry: not a bug in the truncation code, a predictable consequence of a Line 4 allocation that was never sized for what this request type actually needed. The re-derived column doesn't magically make every line generous — Line 3 is still tight against the longest real conversations, which is a correct, honest result: it's the real signal that Chronic Care Check-In needs Chapter 3's compression discipline on top of a correct allocation, not instead of one.

A Second Worked Example: a Smaller Window, a Different Model

The recipe holds under a completely different hard limit too — the steps don't change, only the numbers do. Suppose Vantry also runs a lightweight, locally hosted model for an internal staff FAQ tool with an 8,000-token context window, serving short, single-turn lookups (the same archetype as New Symptom Triage, at a much smaller scale):

staff_faq_budget.py (same recipe, an 8,000-token window instead of 32,000) 
  CONTEXT_WINDOW = 8_000
  RESERVED_OUTPUT = 800          # short, single-paragraph answers
  SYSTEM_INSTRUCTIONS = 400      # small, stable staff-tool prompt
  remaining = CONTEXT_WINDOW - RESERVED_OUTPUT - SYSTEM_INSTRUCTIONS
  # remaining = 8,000 - 800 - 400 = 6,800

  # Short-lookup profile: 45% grounding / 35% history / 20% memory
  grounding_budget = round(remaining * 0.45)   # 3,060
  history_budget   = round(remaining * 0.35)   # 2,380
  memory_budget    = round(remaining * 0.20)   # 1,360
  # 3,060 + 2,380 + 1,360 = 6,800 -- accounts for the full remaining budget

Same five steps, an 8,000-token ceiling instead of 32,000, and the same short-lookup profile from Section 4 because the request shape — not the window size — is what selects the profile. A request type doesn't get a different split just because its model's window happens to be smaller; it gets a different split because its actual content shape is different, which is precisely what TriageLine's team got backwards when Chronic Care Check-In shipped on the same window as New Symptom Triage but with a fundamentally different shape.

Context Engineering Builder Thought Process

Problem: a second request type on an already-budgeted assistant produces a subtly wrong answer, and the team that shipped it followed every rule from the last chapter — real budget, real reserved output, real system-instructions line.

Assumption being made: that a budget which passed audit and load testing for one request type is a property of the system as a whole, safe to reuse anywhere convenient. It isn't — a budget allocation is derived from a specific request type's actual content shape (how long its conversations run, how much grounding material it pulls, how much persisted memory it needs recalled), and a new request type with a different shape needs its own allocation, even on the identical model and window.

What actually distinguishes a well-allocated system: not the presence of a budget, but whether every distinct request type has had its own budget derived against its own real worst-case content, validated before shipping — not inherited from whatever request type happened to ship first.

Why this matters before Module 2: Module 2 (Chapters 3-4) asks you to design short-term and long-term memory policies that operate inside a line's allocated budget — you can't design a sound eviction or recall policy for Line 3 or Line 4 if the number of tokens that line is actually allowed to spend was never derived correctly for the request type in the first place.

Working definition to carry forward: a context budget allocation is a per-request-type artifact, not a per-system one — derived from a hard window limit, a reserved output allowance, a fixed system-instructions cost, and a profile-driven split of what's left across grounding, history, and recalled memory, validated against the worst realistic case before it ships, and re-derived (never silently reused) whenever a new request type's content shape genuinely differs from one that already has a budget.

Points To Remember

  • Allocation happens before a request is sent; diagnosis (Chapter 1's project) happens after a failure is already in production — both use the same five-line ledger, from opposite directions.
  • Reserve Working Space (Line 5) and fix System Instructions (Line 1) first — everything else is a split of what's actually left, not a fraction of the whole window.
  • A budget is derived for a specific request type's real content shape (conversation length, grounding volume, memory volume). Reusing one request type's budget for a differently shaped request type, even on the identical model and window, is the exact gap that broke Talia's medication check — not a missing budget, a misapplied one.
  • Validate every allocation against the worst realistic case (the longest conversation, the fullest memory record) before shipping, not the median case that happens to pass a demo.
  • A tight allocation on one line (Chronic Care Check-In's Line 3, even after correction) is a legitimate, honest signal that a line needs a real compression or eviction policy on top — Module 3's subject, not a sign the allocation math was done wrong.
