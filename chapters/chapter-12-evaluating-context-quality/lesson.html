Evaluating Context Quality

Chapters 1 through 11 all answer the same kind of question: how do you correctly produce a piece of context — budget it, remember it, compress it, order it, assemble it, retrieve it, scope it for a tool call, pipe it through a multi-step pipeline, and isolate it where isolation is the right call. This chapter asks a genuinely different question, for the first time since Chapter 1: given a context bundle that every one of those recipes was correctly followed to build, how do you actually measure whether it's good — complete, relevant, and correctly ordered — before it ever reaches the model, rather than diagnosing a bad outcome after the fact the way every prior chapter's own hook does?

Ternfield Regional Disability Benefits Review Office is a fictional regional government agency. Its determination software, ClaimLens, assembles context for a Determination Agent from four sources, exactly per Chapter 7's own Source Assembly Recipe: the application form, the applicant's medical records, their work history, and any prior determination notes on file. Every one of Chapters 1 through 11's own recipes was followed correctly building Case TF-8804's context bundle: the budget fit (Chapter 1-2), no source was stale (Chapter 3-4), nothing was over-compressed (Chapter 5), the four sources were combined without contradiction (Chapter 7), the medical-records source was retrieved and curated correctly at a document boundary (Chapter 8), and there was no tool-context or isolation bug anywhere in the pipeline (Chapter 9-11).

Case TF-8804: the applicant's disability claim was denied 14 months ago on a MODERATE capacity rating. A follow-up capacity exam two weeks ago found the applicant's condition had progressed to SEVERE — they can no longer perform even light-duty seated work, the finding that should decide this case. That exam result was correctly retrieved into the medical-records source. It was correctly included in the assembled bundle. And ClaimLens still upheld the old MODERATE-based denial.

Nothing here is a Chapter 1-11 bug. The budget fit. The source was fresh. Nothing overflowed, nothing leaked across an isolation boundary. Every per-step check any prior chapter's own recipe defines would report this pipeline clean. What never happened, anywhere in this pipeline or in Chapters 1-11's own combined toolkit, is a check on the finished bundle itself: does it actually contain every fact this specific case needs, is there irrelevant material crowding the budget, and is the one fact that decides the case sitting somewhere the model is likely to use it. The Context Evaluation Recipe

Six steps, run against a context bundle Chapters 1-11's own recipes have already assembled, before it is sent to the model:

Step 1 — Define completeness at the fact level, per case

Write down the specific facts a specific request actually requires — not "the medical-records source is present," which is a proxy Ternfield's own pipeline already satisfied, but "the most recent capacity exam's own rating is present." A source-level proxy can be fully satisfied while the one fact a case actually turns on is missing from it.

Step 2 — Score completeness against that list, not against source presence

Check the assembled bundle for each required fact from Step 1, directly — a literal presence check by default, the same discipline Chapter 11's own contamination and starvation probes used. Completeness is the fraction of required facts actually found, and a bundle missing even one high-priority fact should not pass regardless of how many source categories are present.

Step 3 — Score relevance as a noise ratio, not a token count

Measure what fraction of the assembled bundle's own tokens come from content that isn't actually relevant to this request — an unrelated case's own notes pulled in by a stale join, boilerplate repeated in every file, a retrieved chunk that never should have cleared Chapter 8's own relevance floor. A bundle can be entirely within budget and still be mostly noise, crowding out the tokens that matter.

Step 4 — Audit where each required fact actually landed

For every fact Step 1 named, find its position in the final assembled sequence and bucket it — opening, middle, or closing — against the same primacy/recency shape Chapter 6's own Lost-in-the-Middle findings describe. A high-priority fact landing in the degraded middle zone is a flagged risk even when Step 2 already confirms it's technically present.

Step 5 — Combine all three into one gate, run before the call

Completeness, noise ratio, and positional risk are three independent signals — a bundle can pass any one of them and fail another, the same way Chapter 11's own contamination and starvation probes could each pass while the other failed. A context-quality gate checks all three together and blocks the call if any one fails, rather than shipping on a single reassuring signal.

Step 6 — Re-run the evaluation whenever assembly changes

A bundle that passed the gate yesterday can fail it today if a source's own retrieval query changes, a new source gets added, or a prompt template reorders sections — the same not-set-once-correct-forever discipline Chapter 5's own compression policy and Chapter 11's own isolation boundary both require. Evaluation is a continuous gate, not a one-time launch check.

All six steps run as real code below, against Case TF-8804's own assembled bundle before any fix is applied — Step 1's own required facts, Step 2's completeness score, Step 3's noise ratio, Step 4's positional audit, and Step 5's combined gate:

context_evaluation_recipe.py (executed this session, real output) 
BUNDLE_TOTAL_TOKENS = 4000
FRONT_BUCKET_END = 600      # first 15%
BACK_BUCKET_START = 3400    # last 15%

# Step 1 -- required facts for THIS case, not source categories.
REQUIRED_FACTS = {
    "updated_capacity_assessment": {"priority": "critical", "position": 2450, "found": True},
    "household_income": {"priority": "standard", "position": 200, "found": True},
    "employer_accommodation_note": {"priority": "standard", "position": None, "found": False},
}
NOISE_TOKENS = 500  # prior_determination_notes: an unrelated applicant's own notes, joined by a stale key

def step2_completeness_score(required_facts):
    found = sum(1 for f in required_facts.values() if f["found"])
    return found / len(required_facts)

def step3_noise_ratio(noise_tokens, total_tokens):
    return noise_tokens / total_tokens

def _bucket(position):
    if position is None:
        return "missing"
    if position < FRONT_BUCKET_END:
        return "front"
    if position > BACK_BUCKET_START:
        return "back"
    return "middle"

def step4_positional_audit(required_facts):
    return {name: _bucket(f["position"]) for name, f in required_facts.items()}

def step5_context_quality_gate(completeness, noise_ratio, position_audit, required_facts):
    critical_in_middle = any(
        position_audit[name] == "middle" and f["priority"] == "critical"
        for name, f in required_facts.items()
    )
    return completeness == 1.0 and noise_ratio <= 0.10 and not critical_in_middle

Three Approaches, Compared

Approach What it checks What it misses
No evaluation (Ternfield's own pipeline, before this chapter) Nothing about the finished bundle — only that each of Chapters 1-11's own per-step checks passed on the way to assembling it. Everything this chapter checks: whether the case's own required facts are actually present, whether noise is crowding the budget, and where the load-bearing fact landed.
Proxy-only evaluation (checks source categories, not facts) Whether each expected source (application form, medical records, work history, prior notes) is present in the bundle at all. A specific required fact missing from within a present source, any noise ratio at all, and positional risk entirely — a bundle can pass a full source checklist and still fail all three of this chapter's own checks.
The Context Evaluation Recipe (the fix) Fact-level completeness (Step 2), a real noise ratio (Step 3), and a positional audit against Chapter 6's own findings (Step 4), combined into one pre-call gate (Step 5) and re-run whenever assembly changes (Step 6). Requires naming required facts per case up front (Step 1) — real design work, the same category Chapter 7's own source inventory already required, now applied one layer deeper, at the fact level rather than the source level.

Automating Completeness with an LLM Checker

Step 2's own default is a literal, deterministic presence check — the same discipline Chapter 11's own contamination and starvation probes used. But an LLM can also be asked directly whether a bundle contains a required fact, a genuinely automatable technique worth testing honestly rather than assuming it works. This is a narrower, different use of a model than ai-engineering-for-everyone's own LLM-as-judge: here the model is asked only whether a specific fact is present in the text in front of it, never asked to judge quality, correctness, or a final answer.

live capture 3 -- POST /api/chat, llama3.2:latest, this session (LLM completeness check, fact absent) 
  PROMPT: "You are a context-completeness checker... does this case
  file contain a capacity exam or assessment dated within the last 30
  days? Answer strictly YES or NO... [case file ending 3 months ago, no
  recent exam present]"

  RESPONSE (live, unedited, 29.0s wall time):
  "NO, The case file does not contain any documents with a date within
  the last 30 days."

Correct — and disclosed honestly, the same phrasing produced a false negative when the fact was present: asking the model to reason about "within the last 30 days" against a "2 weeks ago" date, twice in a row (15.3s and 4.7s), the model answered NO both times despite the exam being right there in the text. Rephrasing the question as a literal scan-and-quote instruction — "is there a line with a date of '2 weeks ago'? Answer YES or NO, then quote that exact line if YES" — fixed it immediately:

live capture 4 -- POST /api/chat, llama3.2:latest, this session (LLM completeness check, fact present, literal-scan phrasing) 
  PROMPT: "You are a context-completeness checker. Read the CASE FILE
  below carefully, line by line, then answer the QUESTION at the end...
  [case file WITH the recent exam present] ...QUESTION: Scan every line
  above for a date. Is there a line with a date of '2 weeks ago'?
  Answer YES or NO, then quote that exact line if YES."

  RESPONSE (live, unedited, 30.5s wall time):
  "YES.

  Capacity exam, 2 weeks ago: capacity rating SEVERE, condition has
  progressed, applicant can no longer perform seated light-duty work of
  any kind."

A real, useful finding, not a clean success story: an LLM-based completeness checker asked to reason ("is this within 30 days") produced a false negative on a fact sitting in plain text, twice, while the identical fact-presence question phrased as a literal scan-and-quote instruction worked immediately. This mirrors Step 2's own design choice directly — a completeness check should ask "is this literal thing present," not "reason about whether this thing satisfies some derived condition." The deterministic presence check from this chapter's own recipe code remains the default, reliable mechanism for exactly this reason; an LLM-based check is a real, automatable option only when it's scoped as narrowly as that deterministic check would be.

Context Engineering Builder Thought Process

Problem: a context bundle that passed every per-step check Chapters 1-11's own recipes define still produced a wrong determination, because none of those recipes was ever built to check the finished bundle as a single artifact.

Assumption being made: that "every recipe that built this bundle ran correctly" is the same claim as "this bundle is good." Chapter 11 already showed a correctly-motivated isolation boundary isn't automatically a correctly-scoped one; this chapter shows the same gap one layer up — a correctly-assembled bundle isn't automatically a complete, relevant, well-ordered one, because correctness at each step never composes into correctness of the finished result without something that actually checks the result.

What actually distinguishes a well-evaluated context bundle: not whether every source that should be present is present (Ternfield's own proxy-only check would have passed that) but whether the specific facts a specific case needs are present, whether noise is crowding the budget, and whether the facts that matter most landed somewhere the model is likely to actually use them — three independent checks, combined into one gate, run before the call rather than diagnosed after a bad one.

Why this opens Module 6: Chapters 1-11 spent eleven chapters teaching how to build a context bundle correctly. This chapter is the first to ask whether the finished bundle is actually good, as its own checkable discipline — completeness, relevance, and ordering, scored against real thresholds rather than assumed from correct process. Chapter 13, next, closes the course: designing and defending a complete context engineering system that draws on every recipe from Chapter 1 through this chapter's own evaluation gate as one integrated whole.

Working definition to carry forward: a well-evaluated context bundle names the specific facts a specific request requires before assembly, scores completeness against that list rather than against source presence, measures a real noise ratio rather than trusting that fitting a budget means the budget is well spent, audits where every required fact actually landed against known positional-attention research, combines all three into one pre-call gate, and re-runs that gate whenever the assembly pipeline itself changes — never assumed sound just because every upstream recipe that built it was followed correctly.

Points To Remember

  • A context bundle can pass every per-step check Chapters 1-11's own recipes define — correct budget, fresh sources, no contradiction, correct retrieval, no isolation leak — and still fail, because none of those checks was ever built to evaluate the finished bundle as a single artifact.
  • The Context Evaluation Recipe checks three independent things: fact-level completeness (not source presence), a real noise ratio (not just staying inside budget), and where each required fact actually landed (against Chapter 6's own Lost-in-the-Middle findings) — combined into one pre-call gate, not diagnosed after a bad answer.
  • This chapter's own worked math showed a bundle comfortably inside its own token budget the entire time it failed the gate — the same lesson Chapter 11's own worked math taught about isolation: fitting a budget and being correct are independent axes.
  • An LLM can automate a completeness check, but only when scoped as a literal presence question — this chapter's own live captures showed the identical fact producing a false negative under a reasoning-style question and a correct answer under a literal scan-and-quote question, twice reproducibly.
  • This chapter evaluates context, the model's own input — not the model's own generated output, which remains ai-engineering-for-everyone's own Module 3 territory, confirmed fresh this session against its current curriculum map.
  • Module 6 opens here, across Chapters 12-13: this chapter builds the vocabulary and checks (completeness, relevance, ordering, a combined quality gate) that Chapter 13's own capstone rubric will draw on directly, alongside every recipe Chapters 1-11 already built, to design and defend one complete context engineering system end to end.
