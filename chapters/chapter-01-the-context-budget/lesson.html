Chapter 1 Beginner ~26 min

The Context Budget

A model's context window is not a bottomless notepad — it is a fixed, finite resource, and every single token inside it (a system instruction, a retrieved fact, a turn of conversation history, a tool result) is competing with every other token for a limited, costed budget. This chapter names that budget precisely and builds the core mental model the rest of this course spends twelve more chapters deepening: context engineering is the discipline of deciding what earns a place in that budget, and what doesn't.

Brackwater Home Internet is a fictional regional internet service provider. Its support team fields long, meandering troubleshooting conversations — a customer's WiFi keeps dropping, and diagnosing it properly takes back-and-forth, not one message. An engineer named Devon builds SignalDesk: an LLM-powered chat assistant embedded in the support portal that walks a customer through diagnosis, pulls relevant knowledge-base articles, and can call a tool to check a customer's account and equipment record. Every turn, SignalDesk sends the model a fresh request: the system instructions, whatever knowledge-base articles seem relevant, the full raw transcript of the conversation so far, and any tool output — concatenated, unbounded, no cap.

In every demo Devon runs, SignalDesk is genuinely good — helpful, accurate, patient. Demos are short: five or six turns, then done. It ships. A few weeks later, a real customer named Marisol opens a conversation about a dead WiFi zone in her home office. Turn two, she mentions something that matters a great deal: her address is in one of Brackwater's rural coverage zones, served by an older Gen2 gateway that Brackwater's own documentation confirms does not support the newer "SmartMesh" whole-home feature. SignalDesk acknowledges it, correctly, and the conversation moves on to other troubleshooting steps — channel congestion, interference, cabling.

signaldesk_context.py (what actually got sent to the model, turn 34) 
  def build_request(system_prompt, kb_hits, transcript, tool_output):
      # No budget anywhere in this function. Every source is appended
      # in full, then the whole thing is naively sliced to fit under
      # a hard character cap right before the request goes out.
      raw = system_prompt + "\n\n"
      raw += "\n".join(kb_hits)            # every KB hit ever retrieved this session
      raw += "\n".join(transcript)         # EVERY turn, all 33 of them, unsummarized
      raw += tool_output
      MAX_CHARS = 24_000
      if len(raw) > MAX_CHARS:
          raw = raw[-MAX_CHARS:]           # keeps the END, drops the START --
                                            # turn 2 (the Gen2 gateway fact) is
                                            # the very first thing cut

By turn 34, the conversation has covered a lot of ground — router placement, a firmware update, a cabling check, two different knowledge-base articles pulled in along the way. The raw transcript, KB hits, and tool output together now run well past what fits under SignalDesk's hard character cap, so the truncation in the code above quietly drops everything from the start of the conversation, including turn two. SignalDesk recommends the next logical step, following the pattern the recent turns strongly suggest: enable SmartMesh. Marisol's Gen2 gateway cannot run SmartMesh — a fact SignalDesk itself had correctly stated thirty-two turns earlier and, per Brackwater's own documentation, should have ruled the recommendation out instantly. She spends the next 45 minutes trying to enable a feature her hardware doesn't support, gets nowhere, and escalates to a human agent, who has to rediscover the Gen2 constraint from account records neither SignalDesk's tool call nor its truncated context ever surfaced back to it.

Nothing about this incident required a bad model, a hallucination, or an attack. SignalDesk reasoned soundly from what was actually in front of it at turn 34 — the problem is that what was in front of it didn't include the one fact that mattered most. Worse: even several turns before the hard truncation kicked in, the Gen2 fact was already sitting in the least-attended part of a long context window — early, buried under everything that came after — exactly the position independent research has found LLMs use least reliably, well before that fact was ever physically cut.[2] Two separate context failures, stacked: a fact that had already become hard for the model to use because of where it sat, and then, eventually, a fact that vanished because of a truncation rule with no judgment behind it. That gap — not model quality — is this course's actual subject, and this chapter names the mental model that closes it.

Why This Course Exists

If you've taken `ai-engineering-for-everyone`, you already know to treat a prompt as a versioned software artifact — that course's Chapter 3 builds exactly that discipline: a template composed from named, separately-owned pieces, diffed, reviewed, and shipped like code. Nothing in this chapter re-teaches that, and this course assumes it as a given. But notice something about SignalDesk's incident: its prompt template never changed. The system instructions, the composed structure, the tool contract — all exactly as reviewed and shipped. What changed, turn by turn, was the dynamic content poured into that template's variable slots: which KB articles got retrieved, how much transcript got included, what the tool call returned. A perfectly versioned, perfectly reviewed prompt template can still fail in production, every single request, because of what fills it at inference time — and that gap is exactly what `ai-engineering-for-everyone` Chapter 3 does not cover, by its own explicit scope. This course starts exactly where that one stops.

This course is also not "RAG" (`rag-for-everyone` owns chunking, embeddings, vector stores, and retrieval quality — the discipline of producing a ranked list of candidate context; a retriever with perfect precision and recall still hands off to this course's subject the moment those candidates need to become part of an actual context window). It is not "MCP" or protocol- level tool integration (`mcp-for-everyone` owns how a client and server negotiate and exchange tool calls; what happens to a tool's result once it needs to compete for space in the model's next context window is this course's subject, not that protocol's). And, as above, it is not prompt-template versioning (`ai-engineering-for-everyone` Chapter 3's subject). This course is the discipline that applies once a prompt template is already well-managed, retrieval already returns good candidates, and a tool call already returns a clean result — and something in production still goes wrong because of what actually made it into the window, and where.

The Core Mental Model: The Context Budget

The one sentence to carry through all 13 chapters A context window is a fixed, finite, costed resource — every token inside it competes with every other token for a limited budget, and model performance on that content degrades well before the window's hard limit is even reached. Context engineering is the discipline of deciding, on purpose, what earns a place in that budget, in what order, and what gets compressed, deferred, or dropped.

Unpack why "fixed, finite, costed" is doing real work, because each word maps to a specific failure SignalDesk's incident shows directly:

Fixed: every model has a real context-window limit — Devon's own default assistant model tops out well under what SignalDesk's unbounded transcript-plus-KB-plus-tool-output concatenation eventually demanded on turn 34. A production-support write-up from Anthropic states this precisely: "context, therefore, must be treated as a finite resource with diminishing marginal returns."[1] SignalDesk's own code treated it as effectively infinite until the hard character cap forced a truncation nobody had designed on purpose.

Finite in a way that bites before the hard limit: the same source names a second, subtler failure most teams don't expect: "context rot," where model accuracy declines as token count increases, well before a window fills — driven by an "attention budget" that depletes with each new token.[1] Independent research shows this concretely as a position effect: performance "is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts."[2] That's exactly what happened to the Gen2 fact well before it was ever truncated — buried mid-transcript, it was already the least reliable thing in SignalDesk's context, and the hard truncation that later deleted it outright was a second, compounding failure, not the only one.

Costed: every token sent is metered — money and latency, on every single request, for as long as the context keeps growing unbounded. SignalDesk's turn-34 request was dramatically more expensive and slower than turn 2's, for information that, per the position effect above, was simultaneously becoming less useful to the model the longer and later it got included. A production model-provider guide names the same shape of constraint directly: models "can only handle so much data within the context they consider during a generation request,"[3] and every token spent restating history the model doesn't need is a token not available for something that matters more.

The Context Budget Ledger, as a Working Framework

The mental model above is the "why." The ledger below is the "what, specifically, has to earn a place." Five line items, all drawing from the same fixed, costed budget — every later module in this course deepens the engineering discipline behind at least one line. Treat it the way a working engineer treats any budgeting framework: run it against a real system, don't just recite it.

Line 1 — System Instructions

What it covers: the model's fixed operating contract — role, tone, output format, hard constraints. Small, stable, and (per `ai-engineering-for-everyone` Chapter 3) already a versioned software artifact by the time this course's concerns start.

What Brackwater got right here: SignalDesk's system prompt was fine — well-scoped, unchanged all session. This line item was never the problem, which is exactly why the incident is easy to miss in a code review that only checks the prompt template.

Line 2 — Grounding Context

What it covers: retrieved documents and tool output relevant to this specific turn — the handoff point with `rag-for-everyone` (which produces the ranked candidates) and `mcp-for-everyone` (whose protocol returns the tool result); this course picks up from there.

What Brackwater got wrong: every KB article ever retrieved during the session accumulated in the request, with no eviction policy — including articles no longer relevant to where the conversation had moved on to, silently competing for space against content that mattered more.

What this course builds (Chapter 8): turning a retriever's ranked output into well-formed, budgeted context — not appending every hit ever seen.

Line 3 — Conversation History

What it covers: this session's short-term, turn-by-turn memory. The line item that grows fastest and, unmanaged, crowds out everything else — exactly what happened at Brackwater.

What Brackwater got wrong: the full raw transcript, unsummarized, unbounded, with a blind keep-the-most-recent-characters truncation as the only "policy" — one that guarantees the oldest turns (where Marisol's load-bearing fact lived) are always the first casualty, regardless of how important they are.

What this course builds (Chapter 3): short-term memory that stays within an explicit budget without silently truncating load-bearing content — a real eviction policy, not a character-count accident.

Line 4 — Recalled Long-Term Memory

What it covers: facts persisted across sessions (not just this conversation) and deliberately retrieved back into context for this specific turn — a real decision, not "include everything ever stored about this customer."

What Brackwater got wrong: there was no persistent memory layer at all — Marisol's Gen2 gateway status lives in Brackwater's account system, reachable by the very tool SignalDesk already had access to, but nothing in the pipeline re-checked or re-recalled it once the in-session mention of it was gone. A persistent-memory layer with a real recall policy would have supplied it again independent of the transcript's fate.

What this course builds (Chapter 4): designing what gets stored long-term and what gets recalled back into context for a given turn, and when.

Line 5 — Working Space

What it covers: room deliberately reserved, inside the same fixed window, for the model's own reasoning and output — a real cost that shrinks how much budget the other four lines can spend, easy to forget when "budget" gets treated as only an input-side concern.

What Brackwater got wrong: SignalDesk's MAX_CHARS cap accounted for input content only; a long, detailed troubleshooting response left even less real headroom than the nominal cap suggested, compounding the same-session squeeze on Lines 2 and 3.

What this course builds (Chapter 2): a complete budget allocation across all five lines, output space included, for a given request type and hard context-window limit.

Ledger Walkthrough: What Actually Failed at Brackwater

Trace the hook through all five ledger lines at once, the way a real context-engineering review would — this is the move Chapter 12 formalizes as a repeatable evaluation; Chapter 1's job is to show you can already do a rough version of it today.

Ledger line What was missing What it would have caught
1 — System Instructions Nothing missing here — the template itself was fine. N/A — confirms the failure is not a prompt-template problem, ruling out `ai-engineering-for-everyone` Chapter 3's territory.
2 — Grounding Context No eviction policy on retrieved KB articles; stale hits stayed in the request indefinitely. Dropping KB articles no longer relevant to the current sub-topic would have freed real budget before any transcript truncation was even needed.
3 — Conversation History No summarization, no explicit budget, and a blind end-of-pipeline truncation that always sacrifices the oldest turns first. A real short-term-memory policy (summarize old turns, explicitly pin load-bearing facts) would have kept the Gen2 fact available at turn 34, whether or not it was ever re-stated.
4 — Recalled Long-Term Memory No persistent memory layer at all — a fact available in Brackwater's own account system was never re-recalled once the transcript reference to it decayed. A recall policy that re-checks account-critical facts (equipment generation, coverage zone) every turn, independent of transcript survival, would have supplied the fact a second, independent way.
5 — Working Space No reserved output budget, so a long response shrank real input headroom further than the nominal cap implied. An explicit output-token reservation would have made the real, tighter budget visible before it caused a surprise truncation.

Notice that two separate mechanisms compounded here, not one: the Gen2 fact was already degraded by its position (Line 3, no ordering discipline) well before it was physically removed (Line 3, no eviction policy). A fix that only addressed the hard truncation (say, a bigger context window) would have delayed the failure, not prevented it — the position effect alone would still have made the fact progressively less reliable the longer the conversation ran. That's the real argument for treating this as a budget with real allocation and ordering discipline across every line, not a single knob to turn up.

Context Engineering Builder Thought Process

Problem: a long-running LLM feature gives a confidently wrong answer that contradicts something the system itself correctly said earlier in the very same conversation, with no code change, no model change, and no attacker involved.

Assumption being made: that "the model has a huge context window now, so it'll just remember" is the same kind of guarantee a database gives you when you write a row and read it back later. It isn't — a context window is a per-request construction job, rebuilt from scratch every turn out of whatever the surrounding code decides to include, and a fact's survival depends entirely on whether something in that pipeline deliberately kept it in budget and positioned it where the model can actually use it.

What actually distinguishes a context-engineered system: not a bigger context window or a smarter model, but whether every ledger line has a real, explicit policy — a budget for grounding context that evicts stale material, a short-term memory policy that compresses instead of blindly truncating, a long-term recall policy that doesn't depend on the transcript surviving, and a reserved output allowance that makes the real, tighter input budget visible up front.

Why this matters before Chapter 2: Chapter 2 asks you to design a complete token-budget allocation across all five ledger lines for a new request type, before a single request is sent — you can't do that meaningfully without this chapter's vocabulary for what each line is actually responsible for and how they compete.

Working definition to carry forward: a context window is a fixed, finite, costed resource rebuilt fresh every request; context engineering means every ledger line — system instructions, grounding context, conversation history, recalled long-term memory, and working space — has a real, deliberate policy, not a hope that "more context" or "a bigger window" papers over the gap.

Points To Remember

  • A context window is a fixed, finite, costed resource — every token inside it competes with every other token for a limited budget, and treating it as effectively unbounded is exactly the failure that broke SignalDesk.
  • Model performance degrades before a window's hard limit is even reached ("context rot," an attention budget that depletes with token count) — a bigger window delays a budget failure, it doesn't fix it.
  • Position matters as much as presence: information in the middle of a long context is used less reliably than information at the beginning or end — a real, independently documented effect, not a one-off anecdote.
  • The Context Budget Ledger has five lines: System Instructions, Grounding Context, Conversation History, Recalled Long-Term Memory, and Working Space. A system can have a perfect, versioned prompt template (Line 1) and still fail in production because of what fills the other four lines, fresh, every request.
  • This course is not RAG, not MCP, and not prompt-template versioning — it starts exactly where a well-managed template, a good retriever, and a clean tool result hand off, and asks what actually earns a place in the window from there.

A Note on This Chapter's Live-Testing Limitation

This course's default model setup points the plain openai Python client at a local Ollama server (base_url="http://localhost:11434/v1"), zero cost, zero API key — see docs/course-architecture.md for the full policy. Checked fresh this session before writing this chapter: Ollama's /api/tags endpoint responded normally and confirmed one installed model (llama3.2:latest), but a POST /api/chat completion request did not return within a 20-second timeout. This is the same behavior every sibling TechNaom course has independently reported in this sandbox environment. Consequence, stated plainly: Brackwater's example request-building code and turn-34 outcome above are a realistic, carefully constructed illustration of a real, well-documented failure mechanism (see sources 1-2 below for independently reported versions of the position effect and context-rot mechanism), not a transcript this session actually captured from a running model. No number or claim in this chapter is presented as a live model output. Later chapters that build a runnable compression, memory, or evaluation harness will need to re-check Ollama's chat endpoint before claiming any live output from it, and will disclose the result honestly whatever it is.
