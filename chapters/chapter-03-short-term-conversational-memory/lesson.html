Chapter 3 Intermediate ~30 min

Short-Term Conversational Memory

Chapter 2 taught you to allocate a real token budget for Line 3, Conversation History — a specific number, derived on purpose, for a specific request type. This chapter starts Module 2 and asks the question Chapter 2 deliberately left open: once a long-running conversation actually reaches that budget, what happens next? A correctly sized budget with no real policy behind it fails exactly as badly as no budget at all — just later, and more quietly.

Emberlynn Transit Cooperative is a fictional regional transit agency. Its rider-support chat assistant, RouteLine, handles a request type called "Multi-Leg Trip Planning" — a rider working out a route across several transfers, often over many turns as schedules, fares, and preferences come up. The team behind RouteLine had already read this course's first two chapters: for this request type, on a 24,000-token context window, they ran Chapter 2's own five-step recipe and correctly derived Line 3's budget at 8,680 tokens — reserved output fixed first, system instructions fixed second, and the remainder split by the long-recurring-conversation archetype's own profile. The allocation passed every check Chapter 2 teaches. Nobody skipped a step.

What the team didn't build was a real policy for what happens once a conversation's raw transcript actually exceeds that 8,680-token line. Their context-assembly code did the simplest thing available: a sliding window that keeps whichever most-recent whole turns fit under the budget, dropping the oldest whole turns first the moment the running total goes over. Nothing about this is careless in the way Brackwater's unmanaged SignalDesk was in Chapter 1 — it's a real, working eviction mechanism. It just isn't a policy, in the sense this chapter means the word: it decides what survives purely by recency, never by importance.

routeline_history.py (a real budget, a naive eviction mechanism) 
  LINE3_BUDGET_TOKENS = 8_680  # correctly derived via Chapter 2's recipe

  def build_history(turns):
      # turns: oldest first, each an int token count for that turn.
      # Keep only the most recent whole turns whose sum fits budget --
      # drop whole turns from the FRONT as soon as the total goes over.
      kept = []
      running_total = 0
      for tokens in reversed(turns):
          if running_total + tokens > LINE3_BUDGET_TOKENS:
              break
          kept.append(tokens)
          running_total += tokens
      kept.reverse()
      return kept  # nothing here asks WHICH turn matters -- only WHEN it happened

A rider named Priya opens a Multi-Leg Trip Planning conversation. Turn 1 is a greeting and a destination. Turn 2 is where Priya mentions she uses a wheelchair and needs level-boarding platforms at every transfer — a single, 90-token fact. The conversation runs long: fare questions, a request to avoid a delay-prone line, several rounds of schedule back-and-forth, sixteen turns in total. By the time RouteLine recommends a specific transfer point at turn 16, the sliding window has already dropped turns 1 through 3 entirely — including turn 2 — because the running total of the 13 most recent turns alone already fills the 8,680-token budget. RouteLine recommends a transfer platform with a level change and no elevator. Nothing malfunctioned. The eviction mechanism did exactly what it was built to do: keep the most recent whole turns, drop the rest. It simply never knew that turn 2's 90 tokens mattered more than turn 1's 150 or turn 3's 520, because nothing in the mechanism was designed to know that.

This is a genuinely different failure from both of this course's first two chapters. Brackwater's SignalDesk (Chapter 1) had no budget at all. Vantry's TriageLine (Chapter 2) had a budget sized for the wrong request-type shape. Emberlynn's RouteLine has a correctly sized budget and a working eviction mechanism — the missing piece is a policy that decides what gets evicted based on anything other than when it happened. That policy is this chapter's actual subject.

Why a Budget Alone Doesn't Finish the Job

This chapter uses Chapter 1's five-line ledger and Chapter 2's allocation recipe as a lens, not fresh material — if a real, derived number for Line 3 isn't already a familiar idea, Chapter 2 is where that skill lives, not here. Chapter 3 starts from that number as a given constraint and asks a narrower, later question: given a real Line 3 budget, and a conversation that will eventually exceed it, what governs which turns survive?

Priya's incident shows why "raise the budget" is not, by itself, an answer this chapter accepts. A bigger Line 3 budget delays the moment eviction starts — it doesn't change what the eviction mechanism does once that moment arrives. A sufficiently long conversation eventually exceeds any fixed budget; the only real question is whether the policy governing eviction at that point protects what actually matters, or protects whatever happens to be recent. This chapter's own positioning against the course's neighbors is already established in Chapter 1's "Why This Course Exists" section and isn't re-argued here — one addition worth naming directly: this chapter is not `rag-for-everyone`'s subject either. A retriever decides what candidate documents exist to pull into Line 2; this chapter decides what happens to Line 3's own turn-by-turn conversation history, a completely different line on the ledger, governed by a completely different policy.

The Short-Term Memory Policy Recipe

A production model provider's own context-management guidance names exactly this two-part shape: automatically "clear[ing] stale tool calls and results from within the context window when approaching token limits," while giving developers a way to "save critical information" so it survives regardless of position.[1] Six steps, run in order, for every request type whose conversations can realistically grow long enough to matter:

Step 1 — Start from Line 3's already-allocated budget

Do not re-derive this number. If it doesn't already exist, Chapter 2's recipe is where it gets built; this chapter assumes it as a fixed, real constraint the way Priya's 8,680 tokens were real and correct.

Step 2 — Decide the verbatim window

How many of the most recent turns stay raw and uncompressed. Recent turns carry the most conversational coherence — a model reasoning about "what did the user just say" benefits from exact wording, not a paraphrase, so a real verbatim window is the right default for the newest content, not a shortcut to avoid.

Step 3 — Decide the compression trigger

A real system's own default configuration draws a useful distinction here: a configurable trigger threshold that fires compression before the hard limit is actually reached, and a keep count of how many recent interactions survive once it does.[2] Triggering early, not exactly at the hard budget, leaves room to compress calmly instead of truncating under pressure.

Step 4 — Compress, don't truncate, what falls out of the window

Anything older than the verbatim window still gets represented — as a compact running summary, not silently discarded. This chapter builds only the minimum compression discipline needed to keep short-term memory in budget; the deep mechanics of summarization quality and information loss are Chapter 5's full subject, not re-derived here.

Step 5 — Pin load-bearing facts explicitly

Some facts must survive regardless of how early they occurred — safety disclosures, eligibility-changing facts, medication or dosage changes. A pin is not "recency-immune by luck," it's a deliberate, position-independent reservation carved out of the same fixed Line 3 budget, sized and bounded on purpose (an unbounded pin list just re-creates the original budget problem under a new name).

Step 6 — Validate against the worst realistic long conversation

Replay the longest real conversation shape this request type plausibly produces and confirm pinned facts + the running summary + the verbatim window's actual token sum together fit inside Line 3's real budget — the same worst-case discipline Chapter 2 already established for allocation itself, applied here to the policy that governs what happens once that allocation is actually exceeded.

Three Policies, Compared

Not every request type needs the full six-step recipe. Three real policies cover almost every production case:

Policy What it does When it's the right call What it silently loses
No policy needed Every conversation this request type produces stays well under Line 3's budget, or history is intentionally discarded each session. Short, bounded request types (Chapter 2's "short lookup" archetype); explicitly stateless-by-design sessions. Nothing — there's genuinely nothing to manage yet.
Naive FIFO sliding window Keep the most recent whole turns that fit; drop the oldest whole turns first once the budget is exceeded. Genuinely never — real production systems need at minimum a pinning layer on top of this, per this chapter's own hook. Any fact that happened to occur early, regardless of how important it is — exactly what dropped Priya's accessibility requirement.
Hybrid: pinned facts + running summary + verbatim window Reserve a bounded slice for explicitly pinned facts; compress everything older than the verbatim window into a running summary instead of discarding it; keep the most recent turns raw. Any request type where conversations can realistically grow long enough to exceed Line 3's budget and where any single early fact could plausibly matter later. Fine-grained detail from summarized turns (an accepted, bounded loss — Chapter 5's subject in depth) — never a pinned fact, and never the most recent conversational context.

Two things are visible in this table at once. First, naive FIFO isn't even token-efficient — it evicts whole turns 1-3 (760 tokens) to make room, when turn 2's actual load-bearing content was only 90 of those tokens; a policy that can't distinguish importance from recency also can't be precise about what it throws away. Second, the hybrid policy fits comfortably inside the same 8,680-token budget (8,310 tokens, 370 tokens of real slack) while explicitly protecting the one fact that mattered — proof that the fix here was never "a bigger budget," it was a real policy layered on top of the budget Chapter 2 had already gotten right.

Read that response closely, because it makes this chapter's actual argument better than a clean example would have: the prompt explicitly asked the model to exclude the accessibility requirement ("it is tracked separately"), and the model included it anyway, unedited, exactly as captured. This is not cherry-picked to prove a point — it is the real, first live output this course has captured, and it happens to demonstrate the central risk of relying on a summarizer's own judgment for what to keep: even a direct, explicit instruction to omit a specific fact was not reliably followed. That is precisely why this chapter's hybrid policy does not ask a summarization step to decide whether the accessibility requirement survives — it pins that fact through a separate, deterministic mechanism (Step 5) that never depends on an LLM call's instruction-following at all. A summary is still useful for everything else in this compression, but it is the wrong tool to trust with the one fact that actually has to survive.

Context Engineering Builder Thought Process

Problem: a request type has a correctly derived Line 3 budget, a working eviction mechanism, and still drops a safety-relevant fact from a long conversation.

Assumption being made: that having any working eviction mechanism is the same as having a real memory policy. It isn't — a mechanism decides how eviction happens once triggered; a policy decides what survives, and a mechanism with no policy behind it defaults to the simplest possible rule (recency), which has no way to know a 90-token fact matters more than an 800-token stretch of small talk.

What actually distinguishes a well-managed short-term memory system: not the presence of an eviction mechanism, but whether the mechanism is governed by an explicit policy that separates three concerns — what stays verbatim because it's recent, what gets compressed instead of discarded because it's aged out, and what gets pinned because it's load-bearing regardless of when it happened.

Why this matters before Chapter 4: Chapter 4 asks a related but distinct question — what should a system remember across sessions, not just within one. A system that can't reliably keep a fact alive for the rest of a single conversation has no sound foundation for deciding what's worth persisting to long-term memory in the first place.

Working definition to carry forward: a short-term memory policy is a per-request-type artifact, derived from an already-allocated Line 3 budget, that fixes a verbatim window sized to preserve recent coherence, a compression trigger that fires before the hard limit is reached, a running summary that represents (never silently drops) anything older, and a bounded, explicit set of pinned facts that survive regardless of position — validated against the worst realistic long conversation before it ships.

Points To Remember

  • A correctly allocated Line 3 budget (Chapter 2) is a precondition for this chapter, not a substitute for it — a right-sized budget with a naive eviction mechanism fails exactly as Priya's did: later than an unbudgeted system, but just as silently.
  • Naive FIFO eviction decides what survives by when something happened, never by whether it matters — it is never, by itself, a sufficient production policy.
  • The hybrid policy separates three concerns on purpose: a verbatim window for recent coherence, a running summary for aged-out content (compressed, not discarded), and a bounded, explicit pin list for load-bearing facts that must survive regardless of position.
  • An unbounded pinned-facts list just re-creates the original budget problem under a new name — pinning has to be selective and bounded, or nothing is actually prioritized.
  • Adding a compression policy doesn't remove the need to validate against the worst realistic case — the same discipline Chapter 2 established for allocation applies here to the policy governing what happens once that allocation is exceeded.

A Note on This Chapter's Live-Testing

Re-checked fresh this session, per this course's own standing discipline, and with real news this time: curl http://localhost:11434/api/tags responded normally and confirmed the same installed model (llama3.2:latest). The POST /api/chat endpoint's actual behavior this session was more mixed than a single clean "it works now" result, and it's disclosed honestly rather than rounded up: a first attempt with a 120-second timeout (more patient than Chapter 2's 75 seconds) did not return; a second attempt with a 180-second timeout succeeded, returning a real response after roughly 153 seconds total, almost all of it (about 138 seconds) the model's own cold load time in this sandbox; an immediate follow-up call with the model already warm returned in about 11.5 seconds; but a later call (an early attempt at the compression example below) then timed out twice more, at 60 and 150 seconds, before finally succeeding on a third attempt at 240 seconds in 8.7 seconds flat. In other words, this session did not observe a simple "cold once, fast forever after" pattern — the endpoint hung intermittently even after a successful warm call, consistent with the sandbox having some other periodic cause of latency or contention, not just first-load cost. This is nonetheless the first session in this course to actually capture live model output, not just direct, verified arithmetic — consistent with `ai-engineering-for-everyone`'s own prior finding that this exact hang eventually resolves with a sufficiently patient retry, now independently reproduced here, with the added honest caveat that "resolves" did not mean "stays resolved" within this same session. Every exercise, practice, and project self-check in this chapter still uses deterministic, directly computed data rather than a live call, because this repository's own local_check.sh runs every solution.py under a 20-second timeout — far shorter than several of this session's own observed wait times — so wiring a live call into the graded harness would make the automated checks themselves unreliable. The live capture above is real and unedited (including the model not fully following its own instruction, discussed above), disclosed as illustrative, not as something any graded script in this chapter depends on. A future chapter with more room to warm the model before a graded run, or a documented hosted-provider swap, could reconsider this tradeoff.
