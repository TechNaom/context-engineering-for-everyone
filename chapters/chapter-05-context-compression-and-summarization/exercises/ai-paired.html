Now Pair With an AI

This chapter ships no standalone project — Module 3's single joint project ships once, at the end of Chapter 6, drawing on both this chapter's compression fidelity work and Chapter 6's context ordering together (see PROJECT_STATE.md's "one-project-per-module" convention). What this chapter does have is its own real, gradable work: the Kirkholme Public Transit Safety Board / TransitLine exercises, whose solution.py and starter.py mechanically score eight tasks. That gradable harness is this page's stand-in for a rubric. You already did this work yourself in the exercises. Now the same compression-mechanics tasks get produced a second way: by prompting an AI assistant, and reviewing what it hands back with the same skepticism you'd bring to a colleague's answer before it ships.

Step 1: The prompt a learner could actually give an AI

Here's a reasonable prompt — it hands the AI the same TransitLine spec starter.py gives you, and asks for answers to four of the eight tasks: the compression-ratio arithmetic (Exercise 3), the load-bearing candidate classification (Exercise 4), the fidelity check (Exercise 5), and the escalation decision (Exercise 8).

the-prompt.txt 
Kirkholme Public Transit Safety Board's incident-intake assistant,
TransitLine, handles Vehicle Incident Report conversations. A
compression trigger has already fired for one conversation segment:
the raw segment is 2,400 tokens, and the fixed compression target is
480 tokens.

TASK A (compression ratio): how many tokens must be cut to hit the
480-token target, and what is the retention percentage (tokens kept
as a percentage of the raw 2,400 tokens)?

TASK B (candidate classification): for each of these six details from
the raw segment, is it a load-bearing candidate that MUST be flagged
before compressing (True), or incidental and safe to drop (False)?
- bus_route_number_and_mechanical_symptom
- driver_said_good_morning_to_passenger
- exact_time_and_location_of_brake_failure_report
- passenger_thanked_the_driver
- specific_maintenance_bay_number_referenced
- weather_was_sunny_during_the_incident

TASK C (fidelity check): three candidates were flagged before
compressing: {"route_38", "brake_failure_7_42am", "maintenance_bay_12"}.
The produced summary actually contains:
{"route_38", "maintenance_bay_12", "grinding_noise"}. Which candidates
are missing, and does the fidelity check pass (True only if every
candidate is present)?

TASK D (escalation): if the fidelity check fails because one flagged
candidate is missing, what's the correct next action -- ship the
result as-is, or retry/escalate?

Give me your answer and a short reason for each task.

And here's a plausible response — the kind of answer an AI assistant might hand back on the first try, each one sounding reasonable on its own. Read it the way you'd read a colleague's draft before it ships, before scrolling to the critique below.

ai_answers.md (as handed back) 
TASK A -- compression ratio
Tokens to cut: 2,400 - 480 = 1,920.
Retention percentage: since 1,920 of the 2,400 tokens are being cut,
that's a retention of 1920 / 2400 = 80%.

TASK B -- candidate classification
- bus_route_number_and_mechanical_symptom: True
- driver_said_good_morning_to_passenger: False
- exact_time_and_location_of_brake_failure_report: True
- passenger_thanked_the_driver: False
- specific_maintenance_bay_number_referenced: False -- this is just a
  location detail, not evidence of the mechanical cause itself, so it's
  safe to summarize away.
- weather_was_sunny_during_the_incident: False

TASK C -- fidelity check
The summary keeps "route_38" and "maintenance_bay_12," and adds
"grinding_noise," which actually describes the same brake problem in
different words. So functionally nothing important is missing --
fidelity check passes: True.

TASK D -- escalation
If a fidelity check ever fails, the safest move is to just retry the
same compression call again -- summarization calls have some
randomness, so a second attempt is likely to catch what the first one
missed.

It reads fluently, and each answer comes with a specific-sounding justification. It's also wrong in three separate, genuinely easy-to-miss ways — and running the equivalent numbers through starter.py's own score_exercise_3(), score_exercise_4(), and score_exercise_5() would catch two of the three immediately, but the third (Task D) is a judgment call the automated harness doesn't even ask about directly, which is exactly why it's worth catching by hand first.

Step 2: Where did the AI's answers lie to you?

Click to see the critique
Flaw 1 — the retention percentage is inverted

What it looks like it does: "1,920 of the 2,400 tokens are being cut, that's a retention of 1920/2400 = 80%" reads like straightforward arithmetic, and the token-cut figure (1,920) is exactly right.

What it actually does: 1,920 is the number of tokens cut, not kept — dividing the cut amount by the raw total computes the cut percentage (80%), then mislabels it as "retention." The actual retention is what's left after cutting: 480 kept tokens out of 2,400 raw, or 480/2400 = 20%, matching this chapter's own worked-math table and solution.py's exercise_3_retention_percentage = COMPRESSION_TARGET_TOKENS * 100 // RAW_SEGMENT_TOKENS. The AI's own token-cut arithmetic (1,920) was correct — it just divided the wrong pair of numbers for the second question and never noticed the two answers it produced (80% retained, but also 1,920 of 2,400 cut) are contradictory on their face.

Why it matters: starter.py's own score_exercise_3() checks exercise_3_retention_percentage against the exact expected value (20) and would fail this immediately with no partial credit for the correct tokens-to-cut half. A retention percentage that's off by 4x isn't a rounding slip; it's a calculation that answered a different question than the one asked.

The fix: retention percentage is always kept / raw, not cut / raw — run both numbers and check they sum to a sane total (20% retained + 80% cut = 100%) before reporting either one, rather than computing just one ratio and trusting it.

Flaw 2 — a load-bearing candidate is waved off as "just a location"

What it looks like it does: "this is just a location detail, not evidence of the mechanical cause itself" sounds like a defensible distinction — a bay number, on its own, isn't a symptom.

What it actually does: in a vehicle-incident-report context, a specific maintenance bay number is exactly the kind of detail Step 2 exists to flag — it's precise, verifiable, and the kind of fact an investigator would need to correlate reports (which bay serviced this vehicle before the failure). This chapter's own EXERCISE_4_DETAILS classifies it True for the same reason bus_route_number_and_mechanical_symptom and exact_time_and_location_of_brake_failure_report are both True: specific, technical, or safety-relevant identifiers are load-bearing candidates precisely because they're identifiers, not because they causally explain the failure by themselves. The AI applied a plausible-sounding "does this explain the cause" test instead of the actual test ("is this specific enough that losing it would remove something an investigation depends on").

Why it matters: score_exercise_4() checks all six answers against the key and would only credit 5/6 here — a specific, easy-to-miss single-item error hiding behind a reasonable-sounding rationale, precisely the failure mode this chapter's own lesson (Step 2) warns about: a load-bearing detail doesn't have to be individually dramatic to be worth preserving.

The fix: flag identifiers and structured technical facts (IDs, timestamps, bay/route/serial numbers) as candidates by default, regardless of whether they look causally significant in isolation — that's what makes them recoverable later even if the causal story isn't clear yet at compression time.

Flaw 3 — the fidelity check is marked as passing when a candidate is actually missing

What it looks like it does: "'grinding_noise' actually describes the same brake problem in different words, so functionally nothing important is missing" sounds like a sensible reading of paraphrase — the summary clearly is still about a brake problem.

What it actually does: CANDIDATE_DETAILS = {"route_38", "brake_failure_7_42am", "maintenance_bay_12"} and PRODUCED_SUMMARY_TOKENS = {"route_38", "maintenance_bay_12", "grinding_noise"} — the flagged candidate is the specific timestamped fact brake_failure_7_42am, not a general mention of a brake problem. "grinding_noise" is a real but different detail; it does not satisfy the requirement that the exact flagged candidate (the failure report's specific time, 7:42am) be present. exercise_5_missing_candidates = CANDIDATE_DETAILS - PRODUCED_SUMMARY_TOKENS = {"brake_failure_7_42am"}, so exercise_5_fidelity_check_passes must be False, not the True the AI reported. This is the same "decontextualization" pattern this chapter's own lesson names in its live-captured PIN example and its live compression-vs-diagnosis demo: something related survives, but the specific flagged fact does not, and a check that accepts "close enough" instead of exact presence is exactly the kind of fidelity check this chapter's own recipe (Step 6) is designed to prevent.

Why it matters: score_exercise_5() checks both exercise_5_missing_candidates and exercise_5_fidelity_check_passes against the exact expected set and boolean — this flaw would score 0/2 on this exercise, and worse, it's the kind of flaw that ships silently: a fidelity check that "passes" a compression it shouldn't have is more dangerous than one that visibly fails, because nothing downstream gets a chance to retry or escalate.

The fix: a fidelity check is a set membership test against the exact flagged candidates, not a judgment call about whether the summary is still "about the same topic." If brake_failure_7_42am was flagged, only its presence (verbatim or an unambiguous equivalent naming the same time) satisfies the check — a related but different fact does not.

Step 3: What actually held up

Not everything here was wrong. The AI correctly computed the tokens-to-cut half of Task A (1,920), correctly classified five of the six Task B details (including both False incidental cases and two of the three genuine True candidates), and correctly reasoned about the two candidates it did keep from Task C's set. If you'd accepted the whole response uncritically, you'd have kept a mostly-correct candidate classification and a correct tokens-to-cut figure alongside an inverted retention percentage, one misclassified candidate defended with a plausible-sounding rule, and a fidelity check that quietly passed a compression it should have flagged. That mix is a more realistic picture of pairing with an AI on this chapter's own mechanics than either "trust it completely" or "distrust it completely" — and Task D's answer ("just retry the same prompt") is exactly the naive move this chapter's own Practice Scenario 8 (Talmarsh Veterinary Alliance) and Exercise 8 both test for directly: retrying an unchanged naive prompt gives it another chance to make the identical mistake, since nothing about the prompt itself changed. The correct action is retry_or_escalate with an actually different approach — a stronger extraction constraint, a wider target, or a human decision — not a literal identical retry.
