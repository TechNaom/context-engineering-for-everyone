Chapter 13 Project — L4 Architecture Challenge ~2-3 hours

Project: Castellan Fleet Logistics — Context Engineering System Design

This is the course's Level 4 "Architecture Challenge" — the final project, and a genuinely different shape from every project before it. Castellan Fleet Logistics is a fictional long-haul trucking company with two context-heavy components: DispatchMind, the real-time, multi-agent dispatch copilot the lesson's own worked example walked through in detail, and ComplianceLedger, an internal, asynchronous tool that turns raw ELD/HOS logs into a regulator-ready compliance-report entry, reviewed by a compliance officer before filing. Business problem only — no scaffold, no provided pipeline.

Why this artifact shape, not a starter.py A business problem with no provided pipeline has no fixture data for a Python script to grade against. This project's real deliverable is a written design document — closer to a real architecture-decision record than a filled-in exercise file — though it still includes real, mechanically-checkable arithmetic (whether each component's declared Context Budget Ledger and evaluation gate are actually valid). See ../../quality-audits/chapter-13-audit.md's "L4 artifact-shape decision" section for the full reasoning.
How to do this project Copy DESIGN_DOCUMENT_TEMPLATE.md to your own file and fill in every section for both components, keeping the python code blocks' structure intact. Run python3 self_check.py your_file.md to confirm every section is present and your ledger/evaluation-gate arithmetic is correct. Compare against solution/SOLUTION_DESIGN_DOCUMENT.md, then self-grade against RUBRIC.md.
DESIGN_DOCUMENT_TEMPLATE.md self_check.py solution/SOLUTION_DESIGN_DOCUMENT.md (reference) RUBRIC.md README.md

What you're given

One business problem, two components with genuinely different real profiles (real-time/multi-agent/user-facing vs. asynchronous/single-agent/internal), a required design-document structure, and a mechanical structural self-check for the objectively-checkable parts (section completeness, and whether each component's Context Budget Ledger and evaluation gate are arithmetically valid).

What you produce

A complete, defended design document: for both components, a real Context Budget Ledger (Ch. 1-2) and real short-term memory (Ch. 3), long-term memory (Ch. 4), compression/ordering (Ch. 5-6), source-assembly/retrieval (Ch. 7-8), tool/multi-agent/isolation (Ch. 9-11), and evaluation-gate (Ch. 12) plans at the depth each component's own real shape calls for — plus a cross-component synthesis naming why the two diverge, what would change each profile, and a real shared-infrastructure risk.

Passing bar

24/30 (80%) or higher on RUBRIC.md's six criteria, with no single criterion scoring 0. solution/SOLUTION_DESIGN_DOCUMENT.md is one complete, valid reference response scoring a full 30/30 — not the only correct response, since most of this document's reasoning is intentionally open-ended.
