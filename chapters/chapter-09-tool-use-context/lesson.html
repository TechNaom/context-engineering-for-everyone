Context Engineering for Tool Use

Modules 1 through 4 assumed every candidate source arrived as text: conversation history, retrieved documents, system instructions. A tool call is different in one specific way — the model doesn't just receive content, it also has to be handed a menu of what it's allowed to ask for, and whatever comes back is raw, machine-shaped data, not prose. This chapter, opening Module 5, assumes a tool call already happened, by whatever protocol got it there, and engineers the three things that actually cost tokens because of it: the tool definitions paid for on every single call, the result curated or dumped in raw, and the tool-call history that keeps growing across a multi-step loop.

Points to remember

Sagebrush Regional Field Services Cooperative is a fictional multi-county utility maintenance cooperative. Its dispatch assistant, DispatchLine, helps dispatchers decide whether it's safe to send a field crew to a job site right now, by calling tools: a weather lookup, a crew roster, an inventory check, a GPS router, a customer-history lookup, and seven other registered tools the cooperative had built up over two years of feature requests. By the time this chapter's story starts, every one of those twelve tools worked correctly when called, and the protocol moving requests and results between DispatchLine and each tool — built on an internal RPC layer, not this course's subject — had never dropped or corrupted a message. That is deliberately not this chapter's problem: `mcp-for-everyone` already owns protocol- level tool negotiation, and this chapter assumes a tool call already happened correctly, exactly as it names later in this lesson.

A dispatcher asked DispatchLine whether it was safe to send a bucket-truck crew to Depot 4 right now. DispatchLine called its weather-lookup tool, which returned a real, correct, forty-field JSON payload — station id, latitude, longitude, elevation, temperature, dewpoint, humidity, pressure and its trend, visibility, cloud cover and ceiling, wind direction, sustained wind speed, and (the field that actually decided the answer) wind gust speed and an active high-wind advisory. Nothing about the tool's own execution failed.

dispatchline_tools.py (tool hand-off, before this chapter) 
  ALL_REGISTERED_TOOLS = [weather_lookup, crew_roster, inventory_check,
      gps_router, customer_history, work_order_create, work_order_close,
      parts_reorder, safety_bulletin_lookup, outage_map, fuel_log,
      timesheet_lookup]  # 12 tools, ~230 tokens of JSON schema each

  def build_tool_context(request_type, budget_tokens=260):
      # Every tool definition goes in on every call, regardless of
      # whether this request type ever uses more than one or two of
      # them -- no scoping by request type.
      schema_text = "".join(t.schema_json for t in ALL_REGISTERED_TOOLS)

      # A tool actually gets called; its raw result is appended
      # verbatim -- no field selection, no summarization.
      raw_result = weather_lookup(site="depot_4")  # full 40-field JSON

      combined = schema_text + raw_result
      # Crude char-based cutoff wherever the budget runs out -- can
      # land anywhere, including mid-field, mid-value.
      return combined[:budget_tokens * 4]

Twelve full tool schemas — roughly 2,760 tokens — were paid on every call to this request type, even though "Dispatch Safety Check" only ever uses two of them. That alone left little room for the weather tool's own raw result inside the request type's 260-token tool-output budget. The crude cutoff kept the full station id, coordinates, elevation, temperature, dewpoint, humidity, and pressure fields — and ran out of room three characters into wind_gust_mph, before the number 52 or the active high-wind advisory ever made it in. DispatchLine's answer reasoned from a falling pressure trend, 9.5-mile visibility, and a 24 mph sustained wind reading that was present only because it happened to sit earlier in the raw JSON than the gust field — and concluded the crew could probably go, never once seeing the 52 mph gust reading or the advisory that would have said otherwise. Not because the weather tool failed to report it — it reported it, correctly, every time — but because nothing between the tool call and the model decided which twelve fields of forty actually mattered for this decision, or that a schema list nobody was going to use should not be paid for on every single call.

What This Chapter Owns, and What It Doesn't

This chapter uses Chapters 1 through 8 as a lens, not fresh material — if the budget ledger, the allocation recipe, memory eviction, the Compression Fidelity Recipe, the Context Ordering Recipe, the Source Assembly Recipe, or the Retrieval Integration Recipe aren't already familiar, Chapters 2 through 8 are where those skills live, and none of them are re-taught here. What's genuinely new: a tool call introduces a context cost Chapters 1 through 8 never had to budget for — the tool's own definition, paid on every call whether the tool executes or not — and a result shape (structured, machine-produced data, not prose) that needs its own curation and boundary-safety rules, distinct from Chapter 8's chunk-based ones. And in a multi-step agentic loop, a tool's result from three calls ago can become stale or fully superseded by a more recent call, a staleness problem Chapter 4's own long-term memory work named first, now showing up inside a single session's own tool-call history.

Two boundaries worth naming as directly as Chapter 8's own lesson named its boundary against `rag-for-everyone`: this chapter does not teach how a tool call is negotiated, discovered, authorized, or transported between a client and a server — how DispatchLine's twelve tools got registered, and whether the message that invoked weather_lookup traveled over MCP, a plain function call, or any other mechanism, is `mcp-for-everyone`'s own subject, out of scope here entirely, per the confirmed cross-course positioning restated below. And this chapter does not decide how a tool's result stacks up against other source types — retrieved documents, conversation history, system instructions — once it's well-formed; that is Chapter 7's own Source Assembly Recipe, already built, and this chapter's own output is designed to be handed straight to it as one typed source, the same handoff shape Chapter 8 used for a retrieved document. This chapter's own job sits in between: given a tool call that already happened correctly, by whatever protocol, what earns a place in context because of it, and how much?

Re-confirmed this session: the `mcp-for-everyone` boundary `docs/discovery-notes.md` scoped this chapter, before it was ever built, as deliberately protocol-agnostic relative to `mcp-for-everyone`. This session re-checked that positioning directly against `mcp-for-everyone`'s own current curriculum map (its 13-chapter roadmap, read fresh this session, not assumed unchanged) rather than trusting the original discovery note by default. The Tool Context Recipe

Six steps, run on a tool call's own definitions and results before anything is handed to Chapter 7's own Source Assembly Recipe:

Step 1 — Scope tool definitions to the request type

Don't include every registered tool's schema on every call. DispatchLine's actual pipeline paid roughly 2,760 tokens of schema for twelve tools on every "Dispatch Safety Check" request, when the request type only ever calls weather_lookup and crew_roster. Deciding which tools a given request type is even allowed to reach is a per-request-type decision, the same category of decision Chapter 2's own recipe already required for every other budget line.

Step 2 — Budget each included tool's schema as its own explicit line item

A tool definition's token cost is paid whether or not the model ever actually calls that tool this turn — the schema has to be present for the model to know the tool exists at all. Anthropic's own context-engineering guidance frames the underlying principle directly: "find the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"[1] — a registered tool a request type never uses is tokens spent on zero signal for that request type, every single call.

Step 3 — Curate a tool's raw result before it enters context

Extract only the fields this request type actually needs; never pass a raw API payload through verbatim. DispatchLine's own weather tool returns forty fields; the "Dispatch Safety Check" decision needs three (site, gust speed, advisory). OpenAI's own function-calling guidance states this directly for tool output specifically: keep responses "concise and relevant" rather than returning "an entire object or database result," because "extraneous information" burns tokens and can degrade the response[2] — curation is not optional polish, it is what keeps a verbose API response from crowding out the one field that decides the answer.

Step 4 — Fit the curated result to budget at a field boundary, never mid-object

If a curated result still doesn't fit, drop whole fields by priority — never truncate a structured payload mid-key or mid-value the way DispatchLine's actual cutoff did to wind_gust_mph. A JSON object cut off mid-field doesn't degrade gracefully into a shorter but still-readable fact the way a prose sentence sometimes does — it produces a parse error, a garbled fragment, or (DispatchLine's own case) a field that silently vanishes with no signal it was ever there.

Step 5 — Budget and evict tool-call history across a multi-step loop

In an agentic loop, a tool called once at the start of a session and called again later for the same fact produces two results — keep the current one, and either drop or explicitly mark the earlier one as superseded, rather than letting both sit in history as if equally current. This is Chapter 3's own short-term eviction discipline and Chapter 4's own staleness handling, applied to a category of content — a tool's own result — neither of those chapters had reason to name directly, since neither was written with tool calls in view yet.

Step 6 — Hand the resolved, typed result to Chapter 7's own Source Assembly Recipe

This chapter decides what a well-formed tool-result source looks like; Chapter 7's Source Assembly Recipe, already built, decides how that one source (now correctly typed tool_result, curated and current) stacks up against every other candidate source, and Chapter 6's own recipe after that decides where it sits. Skipping straight from a raw tool response to Chapter 7's inventory step, the way DispatchLine's actual pipeline did, hands Chapter 7 a source it was never designed to receive — the same gap Chapter 8 closed for a retrieved document, closed here for a tool result.

All six steps are small enough to run as real code, not just describe -- here they are as an executed, runnable pipeline against DispatchLine's own Depot 4 scenario, from scoping the 12-tool registry down to the two tools this request type can call, through curating and fitting the weather result, to evicting a superseded tool-call history entry:

full_pipeline.py (executed this session, real output) 
ALL_TOOLS = {
    "weather_lookup": 230, "crew_roster": 230, "inventory_check": 230,
    "gps_router": 230, "customer_history": 230, "work_order_create": 230,
    "work_order_close": 230, "parts_reorder": 230, "safety_bulletin_lookup": 230,
    "outage_map": 230, "fuel_log": 230, "timesheet_lookup": 230,
}
DISPATCH_SAFETY_CHECK_TOOLS = {"weather_lookup", "crew_roster"}
TOOL_OUTPUT_BUDGET = 260

RAW_WEATHER_RESULT = {  # 3 of the real 40 fields shown; rest omitted for brevity
    "station_id": "KSGB4", "wind_gust_mph": 52,
    "advisory": "High wind warning until 6pm",
}
FIELDS_NEEDED = ["station_id", "wind_gust_mph", "advisory"]
FIELD_TOKEN_COST = {"station_id": 8, "wind_gust_mph": 12, "advisory": 20}

def step1_scope_tools(request_type_tools, registry):
    return {t: registry[t] for t in request_type_tools}

def step2_budget_schemas(scoped_tools):
    return sum(scoped_tools.values())

def step3_curate_result(raw, fields_needed):
    return {k: raw[k] for k in fields_needed}

def step4_fit_at_field_boundary(curated, token_cost, budget):
    kept, total = {}, 0
    for k, v in curated.items():
        cost = token_cost[k]
        if total + cost <= budget:
            kept[k] = v
            total += cost
    return kept, total

def step5_evict_superseded(history):
    latest = {}
    for call in history.values():
        key = (call["tool"], call["station"])
        if key not in latest or call["turn"] > latest[key]["turn"]:
            latest[key] = call
    return latest

TOOL_CALL_HISTORY = {
    "call_1": {"tool": "weather_lookup", "station": "depot_4", "turn": 2},
    "call_2": {"tool": "weather_lookup", "station": "depot_4", "turn": 9},
    "call_3": {"tool": "crew_roster", "station": "depot_4", "turn": 3},
}

Three Approaches, Compared

Approach What it does When it's the right call What it gets wrong
Unconditional full-registry, raw-passthrough (DispatchLine's actual pipeline) Includes every registered tool's schema on every call and appends a tool's raw result verbatim, then truncates by raw character count wherever the budget runs out. Never, once a system registers more than a handful of tools or any tool can return a payload larger than a couple of fields — true of nearly every real tool-calling system. DispatchLine's exact failure: ten tool schemas paid for and never used on this request type, and its single most load-bearing field (the wind gust reading) truncated away mid-JSON.
Scoped tools, raw result passthrough Only includes the tools a request type can actually call, but still appends a tool's full raw result verbatim with no field curation or boundary-safe fit. A real, worthwhile improvement over the unconditional registry — worth doing regardless — but not sufficient alone. Correctly drops the ten unused tool schemas, frees real budget, but does nothing about a verbose raw result crowding out its own most load-bearing field if the budget is still tight.
The Tool Context Recipe (the fix) Scopes tool definitions to the request type (Step 1), budgets each schema explicitly (Step 2), curates a tool's raw result to only the fields needed (Step 3), fits the curated result at a field boundary (Step 4), evicts superseded tool-call history (Step 5), and hands the resolved bundle to Chapter 7's own recipe (Step 6). Any system where tools are registered once but used selectively, where a tool's raw result can plausibly be larger than what a request type needs, or where a multi-step loop calls the same tool more than once — true of nearly every real agentic tool-calling system. Requires deciding a per-request-type tool scope and a curation rule for every registered tool in advance — real design work, the same category Chapters 2 and 8 already required for budget sizing and chunk selection, not a new class of cost.

No arithmetic bug turned up here -- like Chapter 7's own re-verification and unlike Chapters 3 and 6's, this chapter's worked-math tables checked out exactly as written, reported honestly rather than assumed.

The fix was never "raise the tool-output budget" (Chapter 2's subject, and the budget was already generous enough at 40 of 260 tokens once the result was correctly curated) or "shrink the weather API's response" (a tool-provider-side change, out of this cooperative's control and out of this chapter's own scope). The fix was deciding, on purpose, which two of twelve tools this request type ever needed defined at all, and which three of forty returned fields actually decide the answer — two decisions the tool's own execution was never responsible for making.

Step 5 in Practice: History Eviction and the Ledger Interplay

Two things the recipe leaves implicit until they're run as real code rather than just described: what Step 5's eviction actually does to a multi-step loop's own history, and how the 260-token tool-output budget used throughout this chapter is only one line item inside Chapter 2's own total window ledger for "Dispatch Safety Check" -- alongside a new line item this chapter adds that Chapter 2 never had to budget for on its own: the scoped tool schemas themselves.

# worsened) and turn 9 (after). Naive history keeps both with no currency

HISTORY = {

def step5_evicted_history_context(history):
    latest_turn = max(h["turn"] for h in history.values())
    return [h for h in history.values() if h["turn"] == latest_turn]

Context Engineering Builder Thought Process

Problem: a tool call executes correctly and returns correct data, and the request type still fails, either by never seeing the field that decides the answer (DispatchLine's own hook story) or by reasoning its way to a coincidentally-matching but ungrounded conclusion from whatever fields happened to survive a truncation (this chapter's own second live capture).

Assumption being made: that "the tool executed correctly and returned correct data" is the same claim as "the context handed to the model is well-formed." Chapter 8 already showed correct retrieval ranking isn't the same as a well-formed retrieved source; this chapter shows correct tool execution isn't the same as a well-formed tool-result source, and adds a cost Chapter 8's retrieved chunks never had — the tool's own definition, paid on every call before any result even exists.

What actually distinguishes a well-engineered tool hand-off: not whether the tool itself executed correctly (every approach in this chapter's own comparison table achieves that) but whether its schema was scoped to the request type on purpose, whether that schema cost was budgeted as its own line item, whether the raw result was curated to only what this request type needs, whether the curated result was fit to budget at a field boundary instead of truncated mid-object, and whether superseded tool-call history was evicted rather than left to accumulate as if every past call were still current.

Why this opens Module 5: Chapters 1 through 8 engineered budget, memory, compression, ordering, multi-source assembly, and retrieval integration for content that arrives as prose. This chapter is the first place a genuinely new content shape enters the picture — a tool's own definition, paid whether or not it's used, and a tool's own result, structured rather than prose, with its own truncation-safety and staleness rules. Module 5's own remaining chapters build on this one directly: Chapter 10 asks the same "what does this specific step actually need" question across a whole multi-agent pipeline, not just one tool call, and Chapter 11 asks when withholding context between steps is the right design choice on purpose.

Working definition to carry forward: a well-integrated tool-use context scopes tool definitions to what a request type can actually call, budgets each included schema explicitly, curates a tool's raw result to only the fields this request type needs, fits that curated result to budget at a field boundary rather than a character count, evicts or marks superseded tool-call history rather than letting it accumulate indefinitely, and only then is handed to Chapter 7's own Source Assembly Recipe as a single, well-formed tool_result source — never assumed well-formed just because the tool itself executed correctly.

Points To Remember

  • A tool executing correctly and returning correct data is not the same as a well-formed tool-result source — the two live captures this session showed a truncated payload can produce either a confidently missing fact or a confident-sounding but ungrounded conclusion that happens to land on the right verdict anyway.
  • A tool's own schema is a token cost paid on every call whether or not the tool is ever invoked that turn — including every registered tool unconditionally, the way DispatchLine's actual pipeline did, spends real budget on zero signal for most request types.
  • The fix is a deterministic six-step recipe, not a bigger budget: scope tool definitions to the request type, budget each schema explicitly, curate a tool's raw result, fit it to budget at a field boundary, evict superseded tool-call history, and hand the result to Chapter 7's own Source Assembly Recipe as one well-formed source.
  • Scoping tools without curating results is a real, worthwhile improvement over an unconditional registry — but it does not fix mid-object truncation of a still-verbose raw result on its own.
  • A structured tool result doesn't degrade gracefully when cut mid-field the way prose sometimes does — it produces a garbled fragment or a field that silently vanishes, with no signal to anything downstream that the cut happened at all.
